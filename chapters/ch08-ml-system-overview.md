## CHAPTER 8. 데이터 분포 시프트와 모니터링

> 한 문장: ML 모델은 배포 직후가 성능의 정점이다. 시간이 지나면서 데이터는 변하고, 모델은 조용히 실패한다. 문제를 빠르게 감지하고 대응하는 모니터링 체계가 프로덕션 ML의 생존 조건!

---

### 8.1 머신러닝 시스템 장애 원인

- ML 시스템은 **운영 지표**와 **ML 성능 지표** 모두 신경 써서 장애가 없는지 점검해야 함
    - 운영 지표 예시: 영어-프랑스어 번역 시스템이 레이턴시 1초 안에 번역문을 출력하는 것
        - 시간 초과, 웹 페이지 404 오류, 메모리 부족 오류, 세그멘테이션 결함 등의 문제라 알아채기 쉬움
    - ML 성능 지표 예시: 출력 중 99%는 주어진 영어/프랑스어 문장을 정확히 번역한 문장이어야 하는 것
        - 정확도 기대치는 약간의 오차를 허용하지만 연달아 발생 시 시스템 장애로 취급함
        - 번역해도 오역이 있는지 바로 알아채기 어려움 = **조용히 실패(fail silently)**

**💡 ML 시스템 장애는 전통적 소프트웨어처럼 에러 메시지가 뜨는 것이 아니라, 모델이 살아있지만 제 기능을 못하는 방식으로 일어난다. 조용히 실패하기에 더 위험하다.**

---

**8.1.1 소프트웨어 시스템 장애**

- 정의: ML에 속하지 않는 시스템에서 발생하는 장애

| 유형 | 설명 |
| --- | --- |
| 의존성 장애 | 시스템이 의존하는 패키지나 코드베이스에 중단이 발생하면 연관된 시스템도 따라서 중단됨 |
| 배포 실패 | 배포 오류로 인한 실패로, 버전이 안 맞거나 시스템에 특정 권한이 누락된 경우 발생 |
| 하드웨어 오류 | CPU나 GPU처럼 모델 배포에 사용되는 하드웨어가 제대로 작동하지 않는 경우 |
| 다운타임 또는 충돌 | AWS 등 호스팅 서비스에서 서버가 다운되어 서비스도 따라 다운되는 경우 |

- ML 오류가 아니라고 해서 무시할 수 없음
- 실제로 구글 대규모 ML 파이프라인 중단 사례 96건 중 **60건이 ML과 직접 관련 없는 오류**였음
    - 분산 시스템 관련: 워크플로 스케줄러나 오케스트레이터에 문제 발생
    - 데이터 파이프라인과 관련: 여러 소스에서 온 데이터를 잘못 결합하거나 부적합한 데이터 구조를 사용
- ML 도입이 초기 단계이기에 시스템 장애가 많이 발생하는 것으로 보임. 차후 기술의 발전에 따라 안정화될 것으로 저자는 기대

**💡 CS 기초 공부를 잘 해두는 것이 정말 중요하다. 특히 분산 시스템에 대해 JD에서 많이 요구하는 이유를 다시 한 번 납득하게 되는 대목.**

---

**8.1.2 머신러닝 한정 장애**

- 전체 장애에서 차지하는 비중은 낮지만 탐지/수정이 어렵고, ML 시스템은 살아있지만 제 기능을 못하게 됨 → **훨씬 더 위험**

> 혹시 파이프라인 버그는 아닌지, 데이터 수집 과정에서 실수는 없었는지를 먼저 확인하자. 생각보다 사람의 실수가 원인인 경우가 많다.

- 모델 배포 후에 발생하는 3가지 문제:

**1) 프로덕션 환경 데이터가 훈련 데이터와 다른 경우**

- 기본적으로 ML 시스템을 만들 때 훈련 데이터(train)와 본 적 없는 데이터(test)가 유사한 분포에서 나온다고 가정하지만, 이는 대개 올바르지 않음
    - 이유 1: 실제 데이터에 내재된 분포는 훈련 데이터에 내재된 분포와 **상이할 수 있음**
    - 이유 2: 현실 세계는 **정상성을 갖지 않음. 모든 것은 변하고, 데이터 분포는 시프트함**
    - 따라서 훈련-서빙 편향을 야기할 수 있음 (모델이 개발 시엔 훌륭하지만 배포 후 성능은 좋지 않은 현상)
- 데이터 시프트가 발생하는 3가지 유형:
    - 특정 이벤트 때문에 갑자기 발생: 유명인이 언급하거나 기존 경쟁자가 가격 정책을 변경해 이에 대응해야 하는 경우
    - 점진적으로 발생: 사회 규범, 문화, 언어, 트렌드 등 시간에 따라 변화하는 경우
    - 계절적 변화로 인한 발생
- 데이터 시프트로 인한 문제 같아보이는 것들은 대부분 ML 시스템의 복잡성이나 잘못된 배포 관행으로부터 비롯한 **내부 오류**인 경우가 많음

**2) 에지 케이스**

- 극단적인 데이터 샘플로 모델이 치명적인 실수를 하게 될 수도 있는 경우
- 보통 동일한 데이터 분포에서 나오지만, 이상한 샘플 수가 급증했을 경우 데이터 시프트를 의심해볼 수 있음
- 자율 주행 자동차, 의료 진단, 교통 관제, e-디스커버리 등 '안전'이 중요한 케이스들이 해당

| 구분 | 이상치 | 에지 케이스 |
| --- | --- | --- |
| 기준 | 통계적 희귀성 | 논리적 경계 |
| 제거 대상? | 경우에 따라 제거 | 보통 보존 |
| 모델 리스크 | 노이즈 가능 | 실제 실패 원인 |
| 테스트 중요도 | 중간 | 매우 높음 |

**3) 퇴행성 피드백 루프 (Degenerate Feedback Loop)**

- 정의: 모델의 예측 결과가 사용자 행동을 바꾸고, 그 행동 데이터로 다시 학습하면서 **편향과 단조로움이 점점 강화되는 ML 장애**
    - 노출 편향, 인기도 편향, 필터 거품, 에코 체임버 등 다양하게 불림
- 사용자에게서 획득한 자연 레이블이 존재하는 작업에서 흔함 (추천 시스템, 광고 클릭률 등)
    - 예: 노래 추천을 받을 때 사용자는 추천 받은 것 중 상단에 있는 노래를 들을 가능성이 커짐

- **퇴행성 피드백 루프 감지:**
    - 온라인: 사용자 피드백 발생 시 반영
    - 오프라인: 시스템 출력 인기도의 다양성 측정을 통해 감지 (온라인보다는 어려움)
        - 항목의 인기도는 **롱테일 분포**를 따르기 마련이므로, 출력의 단조로움 점검으로 감지 가능

- **퇴행성 피드백 루프 교정:**
    - **무작위화**: 추천 시스템에서 순위 높은 항목 외에도 무작위 항목도 함께 보여줘서 피드백을 수집. 다양성을 개선할 수 있지만 너무 무작위성이 높으면 사용자가 흥미를 잃을 수 있음
    - **위치 피처 사용**: 특정 값이 존재하는 위치 또한 피처로서 활용. 위치를 숫자로 처리할 수도 있고, 맨 위에 있는지 boolean 값으로 처리할 수도 있음
    - 위치를 반영한 모델과 위치 반영 고려 없이 예측하는 모델 2개를 만들어 사용하는 것도 하나의 방법

**💡 퇴행성 피드백 루프는 추천 시스템의 가장 흔한 함정이다. "인기 있는 것이 더 인기를 얻는" 구조를 의식적으로 깨뜨리지 않으면, 시스템은 점점 단조로워진다.**

### 8.2 데이터 분포 시프트

- **데이터 분포 시프트 정의**
    - 지도 학습에서 모델이 동작하는 데이터가 시간에 따라 변하는 현상 → 모델 예측도 시간이 지날수록 덜 정확해짐
    - **원본 분포(Source Distribution)**: 모델이 훈련된 데이터의 분포
    - **대상 분포(Target Distribution)**: 모델이 추론을 실행하는 데이터의 분포

---

**8.2.1 데이터 분포 시프트 유형**

- 데이터 분포 시프트 ≠ 개념 드리프트 ≠ 공변량 시프트 ≠ 레이블 시프트 → **세 가지는 데이터 시프트의 하위 유형**
- **프로덕션 환경에서의 실무자 관점:** 어떤 유형의 시프트인지보다 **변화를 처리하기 위해 어떤 행동을 취해야 할지**가 주 관심사

**(1) 공변량 시프트 (Covariate Shift)**

- 입력의 분포는 변하지만 입력이 주어졌을 때 출력의 조건부 확률은 동일
    - 공변량: 주어진 통계적 시행 결과에 영향을 미칠 수 있지만 직접적인 관심 대상은 아닌 독립 변수

- **공변량 시프트가 발생하는 원인**
    1. **데이터 선택 프로세스의 편향**: 특정 클래스의 샘플을 수집하기가 어려움 (샘플 선택 편향 문제와 밀접)
    2. **훈련 데이터의 인위적 변경**: 불균형 데이터셋에서 드물게 발생하는 클래스를 오버샘플링
    3. **능동적 학습 프로세스**: 무작위 대신 휴리스틱에 따라 가장 유용한 샘플 선택 → 훈련 입력 분포가 실제와 달라짐
    4. **프로덕션 환경의 변화**: 환경 혹은 애플리케이션 사용 방식이 크게 변함

- **공변량 시프트 대응 방법**
    - **중요도 가중치 조정 (Importance Weighting)**: 실제 입력 분포와 학습 입력 분포 간의 밀도 함수 비율을 추정 → 이 비율에 따라 학습 데이터에 가중치를 부여
    - **현실적 어려움**: 분포가 어떻게 변할지 미리 알 수 없으며, 모델을 새로운 미지의 분포에 강건하도록 선제적으로 학습시키는 일은 매우 어려움

**(2) 레이블 시프트 (Label Shift)**

- 출력 분포가 변하지만 주어진 출력에 대한 입력 분포는 동일하게 유지
- **공변량 시프트 → 레이블 시프트 (동시 발생 가능)**: 입력 분포가 변하면 출력 분포도 변함


**💡 레이블 시프트는 결과의 비율은 바뀌었지만, 같은 결과를 가진 사람들의 특성은 여전히 같다는 개념. 공변량 시프트와 함께 발생하는 경우가 많아서 실무에서 구분하기 어렵다.**

**(3) 개념 드리프트 (Concept Drift)**

- 입력 분포가 동일하게 유지되지만 정해진 입력에 대한 출력의 조건부 분포가 변함
- 많은 경우 개념 드리프트는 주기적이거나 계절적
- **대응방법: 여러 모델 사용**


**💡 개념 드리프트는 "세상이 바뀌었다"는 의미. 외부 환경이 근본적으로 변하면 같은 집도 다른 가격이 된다. 주기적 패턴은 예측 가능하지만, 갑작스러운 변화는 대응이 어렵다.**

---

**8.2.2 일반적인 데이터 분포 시프트**

- **피처 변화 (Feature Change)**
    - 신규 피처가 추가 / 이전 피처가 제거 / 피처 값의 가능한 범위가 변함
- **레이블 스키마 변화 (Label Schema Change)**
    - Y 값의 가능한 범위가 변하는 경우
    - 레이블 시프트와의 차이:
        - **레이블 시프트**: P(Y)는 변하지만 P(X | Y)는 그대로 유지
        - **레이블 스키마 변화**: P(Y)와 P(X | Y)가 모두 변함

**💡 실무에서는 깔끔한 "공변량 시프트만", "레이블 시프트만" 발생하지 않는다. 피처가 갑자기 NaN이 되거나, 클래스가 추가되거나, 여러 시프트가 동시에 발생한다.**

---

**8.2.3 데이터 분포 시프트 감지**

- 데이터 분포 시프트는 **모델 성능이 저하될 때만 문제**가 됨
- 프로덕션 환경에서 모델의 정확도 관련 지표를 모니터링하면서 변화를 확인 (정확도, F1 점수, 재현율, AUC-ROC 등)

- **그라운드 트루스 레이블의 문제**
    - **모델 개발 중**: 레이블을 이용할 수 있음
    - **프로덕션 환경**: 레이블은 항상 이용 가능한 것이 아님
    - 합리적인 시간 안에 레이블을 이용할 수 있다면 모델 성능에 대한 가시성을 확보하는 데 큰 도움
    - **레이블이 없을 때의 대안** → 관심 있는 다른 분포를 모니터링 (입력 분포 P(X), 레이블 분포 P(Y), 조건부 확률 분포 P(X|Y)와 P(Y|X))

- 업계 내 대부분의 드리프트 감지 방법은 **입력 분포, 특히 피처 분포의 변화를 감지하는 데 중점**

- **통계적 방법**

    **(1) 요약 통계량 비교**
    - 최소, 최대, 평균, 중앙값, 분산, 다양한 분위수
    - 추론하는 동안 피처의 중앙값과 분산을 계산하고 훈련하는 동안 계산한 지표와 비교

    **(2) 2-표본 가설 검정 (Two-Sample Hypothesis Test)**
    - 두 모집단(두 데이터셋) 간의 차이가 **통계적으로 유의한지** 확인하는 방법
    - 어제 데이터를 원천 모집단으로, 오늘 데이터를 대상 모집단으로 설정 → 통계적으로 다르다면 데이터 분포가 시프트했을 가능성이 높음
        - 상대적으로 적은 샘플에서 차이가 감지됐다면 → 아마 심각한 차이
        - 감지하는 데 샘플이 엄청나게 많이 필요하다면 → 그 차이는 크게 걱정할 가치가 없음

- **주요 검정 방법들**
    - **콜모고로프-스미르노프 검정 (KS 검정)**
    - **최소 제곱 밀도 함수 차이 검정**: 최소 제곱 밀도 함수 차이 추정 방법 기반
    - **최대 평균 불일치 (MMD)**: 다변량 2-표본 검정을 위한 커널 기반 기법 (업계에서 MMD를 사용하는 회사를 본 적은 없다고 함)
    - **학습된 커널 MMD (Learned Kernel MMD)**
    - **알리바이 디텍트**: 다양한 드리프트 감지 알고리즘을 구현한 오픈 소스 패키지

- **차원 축소의 중요성**
    - 2-표본 검정은 고차원 데이터보다 저차원 데이터에서 더 잘 작동할 때가 많음
    - 따라서 2-표본 검정을 수행하기 전에 데이터의 차원을 줄이는 편이 좋음


**💡 통계적으로 유의한 차이 ≠ 실용적으로 중요한 차이.**

- **시프트를 감지하기 위한 시간 척도 윈도**
    - **슬라이딩 통계**: 단일 시간 척도 윈도 내에서 계산, 각 시간 척도 윈도의 시작 지점마다 재설정됨
    - **누적 통계**: 더 많은 데이터로 지속 업데이트, 각 시간 척도 윈도의 시작 지점마다 재설정되지 않음
        - 이전 창 정보가 포함되므로 특정 기간에 발생한 사건을 파악하기 어려울 수 있음

**💡 시간 윈도 설정은 예민한 문제다. 너무 짧으면 오탐이 많고, 너무 길면 감지가 늦어진다.**

---

**8.2.4 데이터 분포 시프트 해결**

- **많은 기업의 접근법**
    - 데이터 시프트가 불가피하다고 생각
    - 시프트한 정도와 상관없이 주기적으로 모델을 재훈련
    - 모델을 재훈련하는 최적 빈도는 중요한 결정 사항임에도 많은 기업에서 **실험 데이터 대신 직감을 바탕으로 결정**

- **모델이 프로덕션 환경의 새로운 분포에서 잘 작동하도록 하는 세 가지 주요 접근법**
    1. **대규모 데이터셋으로 모델을 훈련**: 훈련 데이터셋이 충분히 크다면 프로덕션 환경에서 모델이 마주할 모든 데이터 포인트를 가진 통합적인 분포를 학습할 수 있으리라 기대
    2. **새로운 레이블을 요구하지 않으면서 훈련된 모델을 대상 분포에 적응**: 대상 분포의 레이블을 사용하지 않고 공변량 시프트와 레이블 시프트 모두에 대한 모델 예측값을 수정 (연구에서는 인기가 덜한 접근)
    3. **대상 분포에서 레이블이 지정된 데이터를 가져와 모델을 재훈련** (오늘날 업계에서 흔한 접근): 이전 데이터와 신규 데이터 모두를 합쳐 처음부터 다시 훈련하거나, 신규 데이터로 기존 모델을 파인튜닝

### 8.3 모니터링과 관찰 가능성

> 다 확인할 수 없을 정도로 많은 CCTV를 달면, 도둑이 와도 못 잡는다.

- Monitoring(모니터링)과 Observability(관찰 가능성)는 때때로 같은 의미로 사용되지만, 엄연히 다르다.
- **Monitoring(모니터링)**: 문제가 발생했을 때 판단에 도움이 될 수 있는 **다양한 지표를 추적, 측정, 기록하는 작업**
    - 운영지표는 크게 3가지 수준으로 나뉨: 네트워크 / 머신 / 애플리케이션
    - 시스템 가동 여부를 결정하는 조건은 SLO 또는 SLA에 정의
        - 예: SLA에 '레이턴시 중앙값 ≤ 200ms' AND '레이턴시 99% 백분위수 < 2s' 등
        - 이 조건을 충족하지 못한 경우 서비스 제공자가 고객에게 환불
- **Observability(관찰 가능성)**: 시스템에 대한 가시성을 제공하는 방식으로 **시스템을 설정하는 작업**

---

**8.3.1 머신러닝 관련 지표**

- ML 관련 지표 중에는 보통 4가지 artifact: **Metric, Model Output, Feature, Raw Input**

**1. Metric**

- 모델 예측에 대한 사용자 피드백(클릭, 구매, 찬/반 등)을 수신하는 서비스의 경우, 이를 기록하고 추적해야 함
- 피드백을 통해 모델 성능을 개선하기는 어려울지라도, 모델 성능 저하를 확인하는 데에 도움이 됨

**2. Model Output**

- 모델의 아키텍처를 변경하지 않았는데 Model Output의 분포가 변했다면?
    - 높은 확률로 Input Feature의 분포가 변한 것

**3. Feature**

- Feature 모니터링의 첫 번째 단계 = **Feature Validation(피처 검증)**: 피처가 기대하는 스키마를 잘 따르는지 확인
    - Feature Validation 예시:
        1. 최솟값, 최댓값, 중앙값 등이 허용 가능한 범위 내에 있는가? (예: 심박수 30~220 bpm)
        2. 정규 표현식 형식을 만족하는가? (예: 상품 번호가 `^[A-Z]{3}-\d{5}$` 패턴)
        3. 미리 정의된 집합에 속하는가? (예: 결제수단이 {CARD, CASH, POINT, TRANSFER} 중 하나)
        4. 두 피처 값 간에 미리 상정해둔 대소 관계를 만족하는가? (예: 체크인 날짜 ≤ 체크아웃 날짜)
- 기본적인 Feature Validation에 도움이 되는 오픈소스:
    - Great Expectations: https://github.com/great-expectations/great_expectations
    - Deequ(AWS): https://github.com/awslabs/deequ
- 피처 모니터링 수행 시 자주 발생하는 4가지 문제:
    1. 프로덕션 모델의 개수, 각 모델의 피처 개수가 너무도 많은 문제
    2. 피처 모니터링은 디버깅에 유용할 뿐, 모델 성능 저하에는 그다지 유용하지 않다는 문제
    3. 각 피처의 파이프라인 단계가 매우 복잡한 문제 (예: Snowflake 문제인지, Numpy 문제인지, 결측치 처리 문제인지 파악 어려움)
    4. 피처가 따르는 스키마가 시간에 따라 변할 수 있는 문제 (1번 문제와 결합되어 유지보수가 현실적으로 매우 어려움)

**4. Raw Input**

- 보통 ML 팀이 아닌 데이터 플랫폼 팀이 담당하는 경우가 많음

---

**8.3.2 모니터링 도구**

- **로그:**
    - 많은 기업에서 로그를 배치 처리함
        - 장점: Spark, Hadoop과 같은 분산 처리를 통해 효율적으로 처리 가능
        - 단점: 이상 현상에 즉각적으로 반응할 수 없음 → 이를 개선하려면 로그 처리를 스트림으로 전환해야 함

- **대시보드:**
    - High-Level 정보 모니터링을 위한 핵심 지표를 잘 선택하고, Low-Level 지표를 추상화하는 작업이 중요

    | 구분 | 정보의 성격 | 목적 |
    | --- | --- | --- |
    | High-Level | 결과 중심, 비즈니스 영향도 | 의사결정 및 상황 판단 |
    | Low-Level | 원인 중심, 세부 기술 데이터 | 문제 발생 시 원인 분석 |

- **경고 알림:**
    - 경고의 3가지 구성요소:
        1. **When**: 어떤 조건에서 경고를 발생할 것인지 (예: 모델 정확도 90% 미만)
        2. **Where/Who**: 누구에게 어떤 채널을 통해 알림할 것인지 (Slack, Jira, CloudWatch 등)
        3. **How**: 현재 상황을 어떤 방식으로 설명할 것인지 (알림 메시지 양식)

---

**8.3.3 관찰 가능성**

- **'관찰 가능한' 시스템**이란: 시스템 로그 또는 지표만 보고도, 시스템 내부 중 어느 부분의 문제인지를 파악할 수 있는 시스템
    - 모니터링은 **'What(무슨 일이 일어난 건지)'**만을 알려주고, 관찰 가능성은 **'Why(왜 이 일이 일어난 건지)'**를 설명
- 'ML 모델의 해석 가능성' 또한 이 '관찰 가능성' 내에 포함되는 개념
- 시스템 출력을 태그, 식별 키워드 등을 사용해 로깅하면, 관찰 가능성에 유리

**💡 모니터링은 '문제를 찾아내는 데에만' 도움을 준다. 문제를 찾은 다음, '해결'하기 위해서는 연속 학습과 같은 후속 단계가 필요하다.**

**Q1. 퇴행성 피드백 루프 모니터링 방법?**

- **출력 다양성 감소 감지**: 지니 계수(추천 분포의 불평등도), 엔트로피(추천의 다양성), 커버리지(전체 항목 중 실제 추천된 비율) 등을 모니터링
- **롱테일 분포 왜곡 감지**: 상위 1%, 10%, 20% 항목의 점유율 추이를 주간 모니터링
- **포지션 편향 심화 감지**: A/B 테스트로 랜덤 순서 vs 모델 순서 비교, 같은 항목을 다른 위치에 배치했을 때 클릭률 비교
- **사용자 행동 패턴 분석**: 탐색(Exploration) vs 활용(Exploitation) 비율, 신규 항목 발견율, 세션 길이/이탈률 등 간접 지표 모니터링
- **A/B 테스트 기반 감지**: 무작위 주입 실험(무작위를 넣어도 큰 차이 없으면 피드백 루프 의심), 위치 실험(클릭률 차이가 10배 이상이면 위치 편향 심각)

**Q2. 에지 케이스는 무시하는 경우도 있을까?**

A. 에지 케이스는 논리적으로 상황에 맞게 잘 해석하는 것이 중요하고, 이상치는 필요에 따라 제거하는 것이 선택지. 에지 케이스를 무시하는 것은 안전이 중요한 도메인에서는 매우 위험하지만, 비즈니스 임팩트가 낮은 경우에는 비용 대비 효과를 판단해서 결정할 수 있다.

---

**Q3. 조용히 실패하는 ML 모델에 대해서 어떻게 내부적으로 점검할까?**

A. 모델 출력 분포의 변화를 모니터링하고, 사용자 피드백 지표(클릭률, 전환율 등)를 지속적으로 추적하며, 통계적 검정을 통해 입력/출력 분포의 시프트를 감지하는 것이 일반적이다. 사전 예방적으로는 Shadow Deployment(실제 서빙은 하지 않지만 병렬로 예측값을 생성해 비교), Canary Deployment 등의 방법을 활용할 수 있다.
