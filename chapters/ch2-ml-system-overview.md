### 2.1 비즈니스와 머신러닝의 목적

- **비즈니스 지표 우선**: ML 프로젝트의 궁극적 목표는 정확도(Accuracy)보다는 **전환율, 비용 절감, 고객 만족도**와 같은 비즈니스 지표 개선이 우선 목적
    - e.g., 기업은 정확도 0.2% 상승보다 수익 창출(ROI)에 더 관심이 많음
- **가설과 실험**: ML 지표가 비즈니스 지표에 미치는 영향을 파악하기 위해 **가설 설정 및 실험적 증빙**이 필수
- **장기적 관점**: ML 도입 효과는 즉각적이기보다 **장기적 투자**를 통해 큰 가치를 발휘

### 2.2 머신러닝 시스템 요구 사항

- **신뢰성 (Reliability)**: 시스템이 오류, 데이터 이상 등에도 **조용히 실패(Silent Failure)**하지 않고 안정적으로 동작해야 함
- **확장성 (Scalability)**: 데이터량, 트래픽, 모델 수가 증가해도 문제없이 확장 가능해야 함
    - 리소스 관리(GPU, 서버)뿐만 아니라 **아티팩트 관리**도 포함되는 개념
- **유지보수성 (Maintainability)**: 엔지니어, 비즈니스 관리자, 도메인 전문가가 **협업하기 쉬운 구조**(문서화, 버전 관리 등)
- **적응성 (Adaptability)**: 데이터 분포 변화, 비즈니스 요구 사항 변경에 **빠르게 반응**할 수 있어야 함

### 2.4 머신러닝 문제 구조화하기

**2.4.1 머신러닝 작업 유형 (문제 구조화)**

- **문제 정의의 중요성**: 실무 문제를 **입력, 출력, 목적 함수**로 명확히 정의해야 함
- **분류 vs 회귀**: 서로 변환 가능하며, 상황에 유리한 방식을 선택
    - **분류**: 스팸 여부, 부서 라우팅 등 범주 구분
    - **회귀**: 주택 가격 예측 등 연속된 값 출력
    - *Tip*: 문제 구조화 시에 장기적인 유지보수 관점에서도 고려해야 함
        - e.g., 앱 사용 예측 시 회귀(확률)로 구조화하면 신규 앱 추가 시 재학습 없이 피처만 추가하면 되므로 확장성에 유리 (↔ 분류 문제로 구조화 할 경우, 신규 앱 추가 시마다 모델 전체를 재훈련해야 함)
- **이진 vs 다중 클래스 vs 다중 레이블**:
    - **이진 분류**: 클래스 2개 (Confusion Matrix, F1 등 metric 확인 용이)
    - **다중 클래스**: 클래스 3개 이상. 클래스가 수천 개면 **고차원 카디널리티** 문제 발생 (소수 클래스 데이터 불균형 ↑)
    - **다중 레이블**: 하나의 데이터가 **여러 클래스**에 속함 (실무에서 흔하지만 레이블 간 상관관계 등으로 까다로움)
        - e.g., 뉴스 기사가 [기술, 금융]에 동시에 속함

**2.4.2 목적 함수 (Objective Function)**

- **다중 목적 함수 처리**: 시스템의 목적이 여러 개일 때 (e.g., 품질도 높이고 비용도 줄여야 함)
    - **방법 1: Loss 2개를 하나로 결합해서, 모델 1개를 학습**
        - Loss 결합 예시
            
            $$
            \text{loss} = \alpha \cdot \text{loss\_a} + \beta \cdot \text{loss\_b}
            $$
            
    - **방법 2: 각 loss를 갖는 모델 2개를 각각 학습**
        - 모델 output 결합 예시
            
            $$
            \text{output} = \alpha \cdot \text{output\_a} + \beta \cdot \text{output\_b}
            $$
            
        
        **⇒ “목적 함수가 여러 개일 때는 일반적으로 각각 분리하는 편이 좋습니다”**
        
        - 이유: 모델 개발과 유지 관리 측면에서 유리
            - weight를 조절할 때마다 모델을 재학습하지 않아도 됨
            - 각 model의 유지 관리 일정이 다르더라도, 전체 결과를 유지 관리할 수 있음
- ➡️ 방법 2(모델 2개 학습)가 유지보수 측면에서 유리
    - 장점: 모델 개발/유지보수 용이성 및 가중치 조절 시 **재학습 불필요**

### 2.5 지성 vs 데이터

- **데이터 품질의 중요성**: 딥러닝 발전이 데이터 양에 기인했으나, 항상 **데이터 양 $\propto$ 성능**은 아님
- **Garbage In, Garbage Out**: 오래되거나 레이블이 잘못된 데이터는 모델 성능을 저하시킴
    - e.g., 허수 주문이 포함된 의류 판매 데이터

**Q1. 추천 시스템에서 ‘배치 예측’과 ‘온라인 예측’의 차이는 무엇인가요? (p. 63)**

A1. **배치 예측**은 대량의 예측을 미리 생성/저장해두는 방식(넷플릭스 등)으로, 최신성 반영은 느리지만 안정적입니다. **온라인 예측**은 요청 순간 실시간 추론하는 방식(유튜브 등)으로 고도의 개인화가 가능하지만 레이턴시/비용 이슈가 있습니다. 실무에서는 이 둘을 결합한 **하이브리드 구조**도 많이 사용합니다.

**Q2. 반복 프로세스에서 단계를 건너뛰고 되돌아가는 경우(2→6)가 실제로 있나요? (p. 70)**

A2. 네, 흔합니다. 예를 들어 데이터 분석 단계(2)에서 데이터 부족이나 품질 문제가 발견되면, 모델링을 하지 않고 바로 프로젝트 중단 혹은 목표 재설정(6)으로 넘어갈 수 있습니다.

**Q3. 왜 단순히 ‘성능 모니터링’이 아니라 ‘성능 저하를 모니터링’한다고 하나요? (p. 71)**

A3. ML 시스템은 기본적으로 잘 동작한다고 가정하되, **이상 탐지(Anomaly Detection)** 관점에서 접근하기 때문입니다. 문제가 생겼을 때 즉각 알 수 있도록 '정상 범위를 벗어나는 저하'에 초점을 맞춥니다.

**Q4. 계층적 분류(Hierarchical Classification)에서 상위 분류 오류가 하위로 전파되는 문제는 어떻게 해결하나요?**

A4. 상위 단계의 실수가 하위로 이어지는 'Blocking' 현상은 다음 방법들로 해결합니다.

- **추론 방식 개선 (Top-N & Beam Search):**
    - 상위 분류기에서 확률이 높은 **Top-N** 후보를 모두 하위로 전달하여 최종 경로 탐색
- **계층 제약 손실 함수 (Hierarchical Loss):**
    - 분류 체계(Taxonomy)상 멀리 떨어진 클래스로 예측할수록 더 큰 페널티 부여
- **Flat 모델과의 앙상블:**
    - 계층 구조 없이 전체 클래스를 한 번에 분류하는 Flat 모델을 별도로 운영하고, 최종 단계에서 계층 결과와 조합하여 오류 보정
- **전역 학습 (End-to-End):**
    - 모든 계층을 하나의 네트워크로 구성해 동시에 학습함으로써, 하위 계층의 정보가 상위 학습에도 기여하도록 설계

**Q5. 고차원 카디널리티 문제에서 Few-shot Learning 등을 쓰면 데이터 요구량(클래스당 100개)이 줄어들까요?**

A5. 네, 데이터 효율을 획기적으로 높일 수 있지만, 클래스 불균형과 도메인 적합성을 함께 고려해야 합니다.

- 데이터 요구량 감소 (10~50개):
    - 일반적인 학습에 클래스당 100개 이상의 데이터가 필요하다면, Pre-trained 모델을 활용한 Fine-tuning이나 Few-shot Learning 기법을 적용할 경우 클래스당 더 적은 데이터로도 학습이 가능해짐
- 클래스 불균형의 한계:
    - Few-shot 기법은 데이터 효율은 좋지만, 특정 클래스에만 데이터가 극도로 쏠린 클래스 불균형(Class Imbalance)이 심할 경우 모델이 다수 클래스에 편향되어 소수 클래스의 특징을 제대로 포착하지 못하는 한계
- 현실적인 접근법:
    - Transfer Learning: 유사 도메인에서 이미 학습된 가중치를 가져와 미세 조정(Fine-tuning)하는 것이 가장 빠르고 안정적
    - Data Augmentation: 데이터가 부족한 소수 클래스에 대해 데이터 증강을 병행하여 최소한의 샘플 수를 확보하는 전략 필수
