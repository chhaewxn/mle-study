> **좋은 시스템이 반드시 유용한 것은 아니며, 나쁜 시스템이 반드시 유용하지 않은 것도 아니다.**

### 6.1 모델 개발과 훈련

- 어떤 모델을 선택하고, 어떻게 비교, 개선할지에 대한 이야기
- 딥러닝 vs 전통 ML의 대립이 아니라, **문제 + 데이터 + 비즈니스 상황에 맞는 선택**이 핵심

---

#### 6.1.1 머신러닝 모델 평가

- 모델 선택의 기본 마인드 셋:
    - 하나의 문제에는 항상 여러 ML 솔루션이 존재함
    - 그렇기에 모든 모델을 다 보기보다는 문제 유형에 잘 맞는 모델 후보군에서 시작해야 함
    - 문제에 따라 달라지는 활용 가능 모델:
        - 텍스트 분류: 나이브 베이즈, 로지스틱 회귀, RNN, 트랜스포머
        - 이상 탐지: k-NN, 아이솔레이션 포레스트, 클러스터링, 신경망

- **모델 선택 시 기억해두면 좋을 6가지 포인트:**

  (1) 최첨단(SOTA)에 집착하지 말기

  - 논문 성능 ≠ 내 데이터 성능
  - 빠르고 싸고 충분히 좋은 해법이 더 가치 있을 수 있음

  (2) 가장 단순한 모델부터 시작하기

  - 단순 모델의 장점
      - 훈련·배포가 빠름
      - **단순 → 복잡 디벨롭하는 게 모델을 이해하고 디버깅하기 쉬움**
      - 베이스라인으로 활용 가능
  - 복잡한 모델은 성능은 좋을 수 있으나 개선·디버깅 비용이 큼

  (3) 사람의 편향을 주의하기
  
  - 어떤 모델에 더 많은 실험 시간을 쓰면 그 모델이 더 좋아 보임 (시간을 쏟는 이유는 개인의 관심 등에서 비롯됨)
  - 공정한 비교를 위해 실험 조건을 맞춰야 함

  (4) 현재 성과와 미래 성과를 비교 평가하기

  - 지금은 트리 모델이 낫더라도 데이터가 늘면 신경망이 더 좋아질 수 있음
  - 가까운 미래에 개선 가능한 잠재력 + 개선 작업 난이도 고려 필요
  - **학습 곡선**으로 성장 가능성 판단하기 !

  (5) 트레이드오프 평가하기

  - 위양성 vs 위음성 (예: 지문 잠금 해제, 코로나19 환자 선별)
  - 정확도 vs 레이턴시/비용 (예: 복잡한 모델 정확도 높지만 GPU 요구)
  - 성능 vs 해석 가능성 (예: 복잡한 모델 성능 좋지만 결과 해석 어려움)

  (6) 모델의 가정 이해하기

  - = 모델이 가정한 데이터 분포, 상황을 이해하기
  - 가정 종류: 예측 가정, IID, 매끄러움, 계산 가능성, 경계, 조건부 독립, 정규 분포 등
  - 데이터가 가정을 위반하면 성능도 무너짐

#### 6.1.2 앙상블
- **여러 모델의 예측을 결합**해 하나의 예측을 만드는 방법
- ML 대회나 고성능이 중요한 문제에서 매우 흔함
- 단점: 배포·유지보수 복잡
- 장점: 성능 향상 효과 큼. 성능 효과가 커지는 이유는 여러 모델이 **서로 다른 실수**를 하기 때문 ! + 불균형 데이터셋 문제 완화에도 도움이 됨
- 모델 간 상관관계가 낮을수록 앙상블 효과가 커짐 → 그래서 일부러 서로 특성 다른 모델들로 조합하는 경우가 많음

  (1) **배깅(Bagging)**

  - 부트스트랩 데이터 여러 개로 모델 학습
  - 평균 / 다수결로 예측
  - 분산 감소, 과적합 완화
  - 대표 예: 랜덤 포레스트


  (2) **부스팅(Boosting)**

  - 약한 학습기를 강한 학습기로 만듦
  - 예시: XGBoost, LightGBM
 
  (3) **스태킹(Stacking)**

#### 6.1.3 실험 추적과 버전 관리

- ML 실험 추적의 목적
    
    > 훈련 과정에서의 이슈 모니터링 (e.g., Loss가 감소하지 않는 문제, Overfitting, 메모리 부족 등)
    > 
- 이론상 추적 가능한 지표(e.g., Loss Function, Metric 등)를 모두 추적하는 건 **비효율적**
- ML 실험 버전 관리의 목적
    
    > 성공적인 모델링 결과를 **재현**하기 위함
    > 
    - ML 실험에서는 **(1) 코드 버전과 (2) 데이터 버전, 이 두 가지를 모두 관리**해야 함
        
        ➡️ Git을 통한 코드 버전 관리는 업계 표준이 된 반면, **데이터 버전 관리는 아직 그렇지 못함**
        
- 대표적인 ML 모델 실패의 원인들
    1. 이론상의 제약 조건:
        
        > e.g., Decision Boundary가 **선형이 아닌 데이터**를 갖고, **선형 모델을 사용**하는 경우
        > 
    2. 잘못된 모델 구현:
        
        > e.g., 모델 Test 시에는 Gradient 업데이트를 하면 안 되는데, 업데이트한 경우
        > 
    3. 잘못된 하이퍼파라미터 선택
    4. 데이터 문제:
        
        > e.g., 데이터 수집, 전처리 과정 등에서 오류 또는 실수를 범한 경우
        > 
    5. 잘못된 피처 선택:
        
        > e.g., 피처를 너무 많이 사용해서 Overfitting되거나, Data Leakage가 발생하는 경우
        > 
- ML 엔지니어와 연구원의 모델링 꿀팁
    1. **단순하게 시작**하고 **점진적으로 구성 요소를 추가**하기
        
        > 가장 단순한 모델(e.g., 레이어가 1개이거나, Loss function이 매우 단순한 아키텍쳐)로 먼저 설계한 다음, 요소를 하나하나 추가하는 것이 좋다
        > 
    2. **단일 배치에 과적합** 시키기
        
        > 극소량의 Train Set으로 모델을 Overfitting 시킨 다음, **Train Set을 그대로 Inference** 했을 때 도달 가능한 최소 Loss를 달성하는지 확인
        > 
        > 
        > ➡️ 이렇게 했는데도 Overfitting을 달성하지 못했다면, 구현 과정에 문제가 있을 가능성 높음
        > 
    3. **무작위 시드 값 고정**하기

**6.1.4 분산 훈련**

1. 메모리 한계 극복 기법
- 아웃 오브 코어(Out-of-core) 알고리즘: 메인 메모리(RAM)보다 큰 데이터를 처리하기 위해 외부 메모리를 활용하는 알고리즘
- 그래디언트 체크포인팅(Gradient Checkpointing): 모든 그래디언트를 저장하는 대신 다시 계산 가능한 연산 그래프만 저장하여 메모리 사용량을 줄이는 기법
- 기대 효과: 연산 시간은 증가하지만 더 적은 메모리로 큰 모델과 배치를 처리할 수 있음

2. 데이터 병렬 처리 (Data Parallelism)
- 여러 머신에 데이터를 나누어 학습한 뒤 결과를 합치는 방식
- 최신 ML 프레임워크에서 지원하는 병렬화 방식 중 가장 보편적인 방법

| 구분                   | 특징                          | 문제점                                              |
| -------------------- | --------------------------- | ------------------------------------------------ |
| **Synchronous SGD**  | 모든 머신의 연산이 끝날 때까지 대기 후 업데이트 | **Straggler problem(낙오자 문제)**: 연산이 느린 머신 하나가 전체 속도를 저하시킴 |
| **Asynchronous SGD** | 각 머신이 계산을 마치는 즉시 가중치 업데이트   | **Gradient staleness(그래디언트 부패)**: 최신이 아닌 그래디언트로 업데이트될 수 있음 |

 - Synchronous SGD의 straggler problem을 완화하기 위해 Asynchronous SGD가 사용되기도 함

3. 모델 병렬 처리
> 모델이 너무 커서 한 머신에 올릴 수 없는 경우 사용


<img width="391" height="344" alt="image" src="https://github.com/user-attachments/assets/915b498f-679d-40d1-a69d-0b27b53d2da3" />


- 모델의 구성 요소를 여러 머신에 나누어 배치하는 방식
- 예시
  - 레이어 분할: 앞쪽 레이어와 뒤쪽 레이어를 서로 다른 머신이 담당
  - 기능 분할: Forward pass와 Backward pass를 서로 다른 머신이 처리
  - 행렬 분할: 거대한 행렬 연산을 여러 머신이 나누어 수행

**6.1.5 오토ML**

- 기본 철학: ML 전문가의 직관이나 반복 작업을 대규모 연산 자원으로 대체하는 것
- Soft AutoML: ML 알고리즘의 Search 과정을 자동화하는 것
- 즉, 하이퍼파라미터(e.g., Learning Rate, Batch Size 등) 튜닝을 자동화 하는 것
    - 일반적으로는 수동적인 사람이 하이퍼파라미터를 만지작 거림
        
        ➡️ GSD(Graduate Student Descent)
        
    - 인기 있는 프레임 워크로는 아래의 것들이 존재함
        - `auto-sklearn` (Sklearn)
        - `Keras Tuner` (TensorFlow)
        - `Tune` (Ray)
    - (중요) Test Set을 사용해서 하이퍼파라미터 튜닝을 하면 안 됨
        
        ➡️ Test Set에 Overfitting되게 만드는 접근임
        
- Hard AutoML: 단순히 하이퍼파라미터만 튜닝하는 게 아니라, 모델 아키텍쳐와 옵티마이저 선택까지 자동으로 맡겨 버리는 것
  
   ➡️ NAS(Neural Architecture Search)라고 함
    
    - NAS 설정의 3요소
        1. 탐색 공간: 가능한 모델 아키텍쳐 범위를 정의하는 것

        2. 성능 추정 전략: 각 아키텍쳐를 모두 최종 수렴까지 지켜보는 건 비용이 너무 크기 때문에, 어느 중간 시점에서 성능을 평가할 수 있어야 함
            > 
        3. 탐색 전략 (e.g., 무작위 탐색, 강화학습, 진화 등)
            
- ML 모델 개발의 4가지 단계
    - Step 1: ML 도입 전
        
        > ML이 아닌 솔루션(e.g., 휴리스틱)을 먼저 시도할 것
        > 
        > 
        > ➡️ 이를 통해 ML이 필요한지 아닌지를 먼저 판단할 수 있을 것
        > 
    - Step 2: 가장 단순한 ML 모델 사용
        
        > 개발과 배포가 쉬운 가장 단순한 알고리즘으로 시작해서 E2E 파이프라인을 먼저 만들 것
        > 
    - Step 3: 단순한 ML 모델 최적화
        
        > 다양한 Objective Function, Hyperparameter, Feature Engineering, Ensemble 등을 활용해보며 모델 최적화
        > 
    - Step 4: 복잡한 모델 사용
        
        > 단순한 모델을 최적화해 보았음에도 더 개선이 필요한 경우, 그때 복잡한 모델을 사용
        >

### 6.2 모델 오프라인 평가

- **평가의 중요성**
  - ML 시스템 평가 방법을 명확히 이해하지 못하면 가장 적합한 솔루션을 찾을 수 없고 관리자가 ML을 채택하도록 설득하기 어려워짐
  - **이상적으로는 개발 환경과 프로덕션 환경에서 평가 방법이 동일해야 하지만, 현실적으로는 어려움**
      - 개발 환경: 그라운드 트루스 레이블 존재
      - 프로덕션 환경: 레이블 없음 (자연 레이블로 유추 가능한 경우도 있음 → 편향 O)

---

**6.2.1 베이스라인**

> **평가 지표는 그 자체로는 큰 의미가 없음. 비교 기준이 필요함**

- **유용한 베이스라인들**

  **(1) 무작위 베이스라인:** 균등 분포 또는 작업의 레이블 분포에 따라 무작위 생성

  **(2) 단순 휴리스틱**

  **(3) 0 규칙 베이스라인:** 단순 휴리스틱의 특수한 경우 (항상 가장 흔한 클래스로 예측)

  **(4) 인간에 의한 베이스라인:** 전문가와 비교했을 때 모델 성능이 어떤지 파악

  **(5) 기존 솔루션**

  - **ML 모델이 반드시 기존 솔루션보다 좋아야만 유용한 것은 아님**
  - 성능이 다소 떨어지더라도 사용하기가 훨씬 쉽거나 저렴하다면 유용함

> 💡 **'좋은 시스템'과 '유용한 시스템'의 구별 /** 무작위 베이스라인조차 제대로 계산하지 않고 모델 성능에 만족하는 경우가 생각보다 많다. 항상 "이 수치가 정말 의미 있는가?"를 자문해야 한다.

---

**6.2.2 평가 방법**

- **프로덕션 환경에서 원하는 모델의 특성**
  - 강건함 (Robust)
  - 공정함 (Fair)
  - 잘 보정됨 (Well-calibrated)
  - 개연성 있는 결과

- **교란 테스트** 
  - 테스트 분할에 약간 변화를 줘서 모델 성능에 어떤 영향을 미치는지 측정
  - **깨끗한 데이터가 아니라 교란된 데이터에서 가장 잘 작동하는 모델을 선택**

- **주의**: 모델이 잡음에 민감할수록 유지 관리가 더 어려워짐
  - 사용자 행동이 조금만 변해도 모델 성능이 크게 저하됨
  - 적대적 공격에 취약해짐

> 💡 실험실에서 완벽한 데이터로 학습한 모델(= HAPPY PATH)이 현실에서 망가지는 경우가 너무 흔하다. "지저분한 현실"을 미리 시뮬레이션하는 것이 핵심!

- **불변성 테스트** 

  - **입력에 특정 변경을 적용했을 때 출력이 변해서는 안 됨**
  - **이러한 일이 발생한다면 모델에 편향이 존재하는 것이므로 성능이 아무리 좋아도 사용할 수 없음**

- **편향 해결책**

  - 나머지 입력은 동일하게 유지하고 민감 정보만 변경해 출력이 바뀌는지 확인
  - 모델 훈련에 사용한 피처에서 민감 정보를 최우선으로 제외

---

- **방향 예상 테스트** 

  - **원칙**

    - **입력에 특정 변경을 적용했을 때 출력이 예측 가능한 방향으로 변해야 함**
    - **출력이 예상과 반대로 움직인다면 모델 학습이 올바르게 이뤄지지 못했을 수 있음**

- **모델 보정** 

  - ML 실무에서 간과되는 경우가 많지만 **모든 예측 시스템에서 매우 중요한 속성**

- **보정된 정도 측정 방법**

  - 모델이 확률 x를 출력한 횟수와 예측이 맞은 빈도 y를 세어보고 y에 대한 x를 플롯
  - **완벽하게 보정되었다면** 그래프상 모든 데이터 포인트에서 x와 y가 동일
  - 사이킷런: `sklearn.calibration.calibration_curve`로 이진 분류기의 보정 곡선 그리기

- **일반적인 모델 보정 방법**

  - **플랫 스케일링 (Platt Scaling)**: 사이킷런 `sklearn.calibration.CalibratedClassifierCV`

- **신뢰도 측정** 

  - **확실한 모델 예측 내용만 보여주고자 할 때**
    - 그 확실한 정도는 어떻게 측정?
    - 예측을 보여주기로 결정하는 확실성의 임곗값은 얼마?
    - 예측이 임곗값 미만으로 나온다면 무엇을 해볼 수 있을까?

  - 사람의 피드백으로 재학습
  - 사용자에게 추가 정보 요청

**슬라이스 기반 평가** 

**슬라이싱:** 데이터를 하위 집합으로 분리하고 각 하위 집합마다 모델의 개별 성능을 확인하는 것

**흔한 실수**

- 전반적인 F1이나 전체 데이터에 대한 정확도 같이 **투박한 지표에 너무 집중**
- **슬라이스 기반 지표에는 충분히 주의를 기울이지 않음**

**사례: 사용자 이탈 예측 모델**

- 유료 사용자는 무료 사용자보다 훨씬 더 중요
- **모델의 전체 성능에 초점을 맞추면** 중요 슬라이스(유료 사용자)에서 성능이 저하되더라도 모르고 넘어갈 수 있음

**심슨의 역설**

- 어떤 추세가 여러 데이터 집단에 나타나지만 **집단을 결합하면 사라지거나 반전되는 현상**
- **집계가 실제 상황을 은폐하고 모순되게 할 수 있음**

**슬라이스 기반 평가의 이점**

1. 전체 및 중요 데이터에서 모델 성능 개선
2. 잠재적인 편향 감지
3. ML과 상관없는 문제 발견
4. 이해관계자가 ML 모델을 신뢰하도록 설득할 수 있는 확신

**중요한 슬라이스를 찾는 접근법**

1. **휴리스틱 기반**
    - 데이터와 작업에 대한 도메인 지식 사용
2. **오류 분석**
    - 잘못 분류된 데이터 포인트를 수작업으로 분석하고 패턴 찾기
3. **슬라이스 파인더**
    - 슬라이스 탐색 프로세스를 체계화하는 연구
    - 빔 검색, 클러스터링, 의사 결정 알고리즘으로 슬라이스 후보 생성
    - 명백히 나쁜 후보를 걸러내고 남은 후보의 순위 지정

> 💡 전체 정확도 95%에 만족하다가 특정 사용자 그룹에서 성능이 60%라는 걸 뒤늦게 발견하는 경우가 너무 많음. "평균의 함정"을 조심해야 함. 슬라이스 기반 평가는 공정성뿐 아니라 실제 비즈니스 임팩트를 측정하는 핵심 도구!

**Q1. 앙상블이 불균형 데이터셋 문제 완화에도 도움이 되는 이유는 무엇인가요?**

A. 소수 클래스가 “여러 번” 학습에 등장하게 됩니다. 부스팅을 할 경우엔 ‘틀린 샘플’에 집중하게 되므로 자연스레 소수 클래스에 관심을 갖게 되고, 이에 따라 여러 모델의 시각을 합쳐 편향을 감소시키게 됩니다. 정리하면, 여러 번, 다양하게 학습하기 때문에 불균형 완화에 도움이 됩니다.

**Q2. 슬라이스 기반 평가에서 중요한 슬라이스를 찾는 게 예술에 가깝다고 했는데, 실무에서는 보통 몇 개 정도의 슬라이스를 모니터링하는 것이 좋을지?**

A. 실무에서는 슬라이스가 너무 많으면 관리가 어려워지기 때문에 보통 핵심 슬라이스 5~10개 정도를 모니터링합니다. 초기에는 다양한 슬라이스를 탐색적으로 살펴본 뒤, 성능 차이가 크게 나타나거나 비즈니스적으로 중요한 슬라이스를 중심으로 추려서 운영 단계에서 지속적으로 관찰합니다.

**Q3. 교란 테스트에서 교란과 노이즈의 기준은 어떻게 정하나요?**

A. 보통 의미와 정답(label)이 유지되는지 여부를 기준으로 구분합니다. 사람이 봤을 때 여전히 같은 의미라면 교란(perturbation)으로 보고, 의미가 바뀌거나 정답이 달라질 수 있다면 노이즈로 간주합니다.

**Q4. 방향 예상 테스트를 역으로 이용해 모델을 조작하거나 의도된 편향을 주입할 수 있지 않나? (→ 불변성 테스트 위반)**

A. 이론적으로는 가능하지만, 이를 방지하기 위해 보통 불변성 테스트와 함께 사용하고 다양한 테스트 케이스를 구성합니다. 이렇게 하면 특정 특징에 과도하게 의존하는 편향이 모델에 주입되는 것을 줄일 수 있습니다.
