## CHAPTER 11. 머신러닝의 인간적 측면

> 한 문장: ML 솔루션은 기술적인 것이지만, ML 시스템 설계는 기술 영역에 국한되지 않는다. 사용자 경험, 팀 구조, 그리고 책임 있는 AI까지 고려해야 진짜 프로덕션 ML이 완성된다!

---

### 11.1 사용자 경험

- ML 시스템의 특성
    - 확률론적(비결정적)
    - 대부분 맞지만 항상 맞지는 않음
    - ML 시스템 규모가 커지면 레이턴시가 길어질 수 있음

---

**11.1.1 사용자 경험 일관성 보장하기**

- **문제**
    - 같은 사용자, 같은 입력이라도 시기에 따라 다른 예측 가능
    - 하지만 사용자는 일관성을 기대하며 서비스를 사용할 것
- **해결**
    - 특정 조건(예: 필터 적용한 경우)에서는 추천을 고정
    - 다른 특정 조건(예: 목적지를 변경한 경우)에서는 새로운 추천 제공
    - 이를 **"일관성-정확도 트레이드오프"**라고 부름

---

**11.1.2 '대부분 맞는' 예측에 맞서기**

- **문제**
    - 생성형 모델은 80~90% 정도 맞는 결과를 생성 → **항상 옳지는 않음**
    - 사용자가 수정할 수 없다면(전문가가 아니라면) 예측 결과의 실질적 가치는 낮음
- **해결**
    - 동일 입력에 대해 여러 예측을 생성하고, 그 중에서 사람이 선택하거나 수정
    - **Human-in-the-loop 구조** 활용
        - 의료영상 판독 보조: AI가 이상 징후를 표시하면 의사가 최종 판독
        - 고객 응대 챗봇: 복잡한 문의는 사람이 응답
        - 콘텐츠 검열: AI 분류 → 사람이 최종 승인

---

**11.1.3 원만한 실패**

- **문제**
    - 일부 입력에서 추론 시간이 과도하게 길어짐
    - 특히 순차 모델에서 자주 발생
- **해결**
    - 백업 모델 사용
        - 주 모델: 정확하지만 느림
        - 보조 모델: 덜 정확하지만 빠름
    - 일정 시간 초과 시 자동 전환 (예: 주 모델이 N밀리초보다 오래 걸리면 백업 모델 사용)
    - 속도-정확도 트레이드오프 관리 필요

**💡 ML 시스템은 "맞냐 틀리냐"만이 아니라, 사용자가 어떻게 경험하느냐가 핵심이다. 일관성, 수정 가능성, 그리고 실패 시 대응 전략까지 설계해야 한다.**

---

### 11.2 팀 구조

**11.2.1 크로스-펑셔널 팀 협업**

- ML 프로젝트에는 다양한 역할이 포함됨: 데이터 과학자, ML 엔지니어, 플랫폼/DevOps, 도메인 전문가(SME)
- **SME의 역할은 단순 레이블링을 넘음**
    - 문제 정의, 피처 엔지니어링, 오류 분석, 모델 평가, 예측 결과 표현 방식 결정(UI/UX) 등
    - 프로젝트 수명 주기 전반에 참여해야 효과적
- **협업의 어려움:**
    - ML의 한계를 비전문가에게 설명하기 어려움
    - 도메인 지식을 코드로 버저닝하기 어려움
    - 책임 범위 불명확
- 이를 해결하기 위해 no-code/low-code 플랫폼 등장 (현재는 레이블링, 품질 보증, 피드백 정도의 단계에만 머무름)
- 개발 관련 깃 권한 부여 등 없이도 프로젝트에 잘 참여할 수 있도록 해야 함

---

**11.2.2 엔드-투-엔드 데이터 과학자**

- **접근법 1: 별도의 팀을 구성해 프로덕션 관리하기**
    - 데이터 과학팀: 모델 개발 / 플랫폼팀: 배포 및 운영 전반 처리 담당
    - 문제:
        - 커뮤니케이션 및 조정 오버헤드
        - 디버깅 복잡: 사내의 결과물이 아닐 수도 있어 책임자 찾기가 어려울 수 있음
        - 책임 미루기 가능성 높아짐
        - 큰 그림을 보기 어려워, 전체 최적화 어려움

- **접근법 2: 데이터 과학자가 모델 개발부터 배포까지 전체 담당**
    - 문제:
        - 인프라와 ML은 서로 다른 전문성
        - 모든 기술을 갖춘 인재는 희소
    - 데이터 과학자가 인프라까지 모두 잘하기를 기대하는 것은 비현실적
        - 앱 개발자가 리눅스 커널의 작동 방식을 알기는 어려운 것처럼
    - **해결책은 "더 많은 능력"이 아니라 "더 나은 추상화 도구"**
    - 인프라 복잡성을 숨겨주는 플랫폼이 있어야 엔드-투-엔드 모델이 현실적으로 가능해짐

**💡 팀 구조의 핵심은 "누가 더 많이 아느냐"가 아니라 "어떻게 협업하느냐"다. 좋은 추상화 도구와 명확한 역할 분담이 답이다.**

**11.3.1 무책임한 AI: Case Study**

> 여러 AI 사고 예시: https://incidentdatabase.ai/

**Case 1: Ofqual(오프퀄) 자동 채점기 (2020년)**

- 배경: 코로나19로 인해 대입 시험(A-레벨)이 취소되자, 영국의 교육 규제 기관인 오프퀄이 알고리즘으로 성적을 부여하기로 함
- **사고 원인**
    1. **잘못된 목표 설정 (학교 간 형평성 우선):** 알고리즘은 '개별 학생의 실력'보다 '학교의 과거 성적 분포'를 유지하는 데 최적화됨 → 과거 성적이 좋지 않았던 학교의 우수한 학생들이 낮은 점수를 받게 됨
    2. **소외 계층 불이익:** 소규모 학교는 데이터 부족으로 교사 평가를 그대로 사용 → 학생 수가 많은 공립 학교나 소외 계층 학생들은 알고리즘의 제약을 받아 불이익
    3. **투명성 부족:** 성적 발표 당일까지 알고리즘의 구체적인 작동 방식을 공개하지 않음 → 외부 전문가의 검토나 대중의 비판을 수렴할 기회를 놓침
- **핵심 교훈:** 모델의 목표가 윤리적으로 올바른지 검토해야 하며, 개발 과정을 투명하게 공개해 독립적인 검증을 받아야 함

**Case 2: 피트니스 앱 스트라바(Strava)의 익명 데이터 위험성 (2018년)**

- 배경: 피트니스 앱 스트라바가 사용자들의 운동 경로를 모아 만든 '히트맵(Heatmap)'을 공개
- **사고 원인**
    1. **익명화의 한계:** 군인들이 기지 내에서 반복적으로 운동한 경로가 히트맵에 굵게 나타나면서, 비밀 군사 기지의 위치와 순찰 경로가 전 세계에 노출
    2. **기본 설정의 문제 (Opt-out):** 많은 사용자가 디폴트 데이터 수집 허용 설정이 켜져 있는지조차 몰랐고, 설정을 바꾸는 방법도 까다로웠음 → 처음부터 데이터를 수집하지 않는 **옵트인(Opt-in)** 방식을 디폴트로 설정하는 것이 중요

**Extra Cases**

- **동의 범위를 벗어난 '목적 외 재사용' (Function Creep):** 특정 목적을 위해 수집된 데이터가 사용자가 예상하지 못한 AI 학습이나 상업적 용도로 활용되는 경우 (예: 고객 상담 일지가 AI 챗봇 학습에 사용자 몰래 사용, 사진 백업 데이터가 이미지 인식 모델 학습에 사용자 몰래 사용)
- **설명 불가능성으로 인한 동의의 역설 (의료 AI 사례):** AI가 표준 가이드라인과 다른 공격적인 치료법을 제안했는데, 환자는 나중에야 AI가 의사 결정에 개입했음을 알게 되는 블랙박스 문제

**11.3.2 Responsible AI 프레임워크**

**방법 1: 모델 bias의 출처 찾아내기**

> ML에서의 bias는 워크플로 전체 중 어디에서나 발생 가능하기 때문에, bias를 해결하기 어려움. 각 질문들을 체크리스트처럼 활용하면서 Responsibility를 점검할 수 있다.

1. **훈련 데이터 (Representation Bias)**
    - 모델 학습에 쓰인 데이터가 실제로 처리할 데이터를 대표할 수 있는가?
    - 그렇지 않은 경우, 데이터가 적은 사용자 그룹에 대해 편향적이 될 수 있음
        - '데이터가 적은 사용자 그룹'이란 소수 Label만이 아니라, 소수 Feature까지 아우르는 개념
    - **편향이 생기는 이유:** ML 모델은 전체 손실(Loss)을 최소화하는 방향으로 학습하므로, 90%를 차지하는 그룹 A에서 잘 맞고 10%인 그룹 B에서 틀린다면 그룹 A의 특징을 우선적으로 학습

2. **레이블링**
    - 어노테이터가 주관적인 경험에 의존하지 않고 있는가?

3. **피처 엔지니어링**
    - 모델의 결정이 민족, 성별, 종교 등 법적으로 보호되는 계층과 상관관계가 있는 정보에 의존하고 있지는 않은가?
    - 이러한 변수를 **'프록시 변수 (Proxy Variables)'**라고 함 (예: 우편 번호, 졸업장 등)
    - **Disparate Impact(불균등 영향) 완화 방법:**

| 기법 | 완화 단계 | 핵심 목적 |
| --- | --- | --- |
| Disparate Impact Remover (DIR) | 전처리 | 데이터 분포 자체를 공정하게 수정. 보호 속성에 따라 결과가 달라지지 않도록 Feature 값을 수정하되 그룹 내 순위는 보존 |
| IBM AIF360 | 전체 과정 | 70개 이상의 공정성 지표 제공 + 다양한 편향 완화 알고리즘 내장 |
| H2O Infogram | 변수 선택 | 관련성(Relevance)과 안전성(Safety) 2차원 평면에서 변수를 평가하여, 프록시 역할을 하는 부적격 변수를 식별/제외 |

4. **모델의 목표**
    - 모델의 최적화 목표가 모든 사용자에게 공평하게 적용될 수 있는 목표인가?

5. **평가**
    - 다양한 사용자 그룹에 대한 모델 성능을 검증하기 위해, **슬라이스 기반 평가** 등 세분화된 평가를 수행하고 있는가?
    - 공정하고 적절한 평가 데이터가 존재하는지가 중요

---

**방법 2: 서로 다른 요구 사항 간의 트레이드오프 이해하기**

- **트레이드오프 1: 개인 정보 보호 vs 정확도**
    - **Differential Privacy(차등 개인 정보 보호):** 데이터셋 전체의 통계적 패턴은 유지하면서, 개별 사용자의 정보는 식별할 수 없도록 노이즈를 섞는 방식
    - 정보를 꽁꽁 숨길수록(보안 강화) 예측 정확도는 떨어짐
    - 정확도 하락이 모두에게 공평하지 않음 → 데이터 양이 적은 소수 그룹일수록 노이즈에 의해 정보가 더 많이 뭉개짐

- **트레이드오프 2: 간결함 vs 공정성**
    - Pruning, Quantization 등 모델 압축을 통해 "정확도가 1%밖에 안 떨어졌으니 성공"이라고 생각하기 쉬움
    - 하지만 그 1%의 오차가 **어디서** 발생했느냐가 문제 → 전체 평균은 높아도 특정 그룹에 대한 정확도만 대폭 하락했을 수 있음
    - ML 모델은 효율을 높이기 위해 **데이터가 적은 쪽(롱테일 클래스)의 정보를 먼저 버리는 경향**이 있음
    - 단순히 "가벼워졌다"고 좋아할 게 아니라, 모델 압축 과정에서 특정 집단이 소외되지 않았는지 꼼꼼히 감시해야 함

---

**방법 3: 사전 대응하기**

- ML 시스템이 사용자의 삶에 어떤 영향을 미치는지, 어떤 편향을 가지는지 미리 파악해야 함
- NASA의 연구에 따르면, SW 개발에서는 프로젝트 수명 주기의 단계가 넘어갈수록 오류 비용이 몇 배씩 증가

---

**방법 4: 모델 카드 생성하기**

- ML 모델의 훈련/평가에 대한 정보를 담은 모델 카드를 제공
- **모델 카드의 목표:** 이해 관계자가 배포를 위한 후보 모델을 비교할 때 전통적인 metric뿐만 아니라, 윤리적 관행과 보고를 표준화하기 위함
- 참고 논문: Mitchell, Margaret et al. "Model Cards for Model Reporting." Proceedings of the Conference on Fairness, Accountability, and Transparency (2018)
    - 링크: https://arxiv.org/abs/1810.03993

**Responsible AI 체크리스트**

- 모델 학습에 쓰인 데이터가 **실제로 처리할 데이터를 대표**할 수 있는가?
- **어노테이터가 주관적인 경험에 의존**하지 않고 있는가?
- 모델의 결정이 민족, 성별, 종교 등 **법적으로 보호되는 계층과 상관관계**가 있는 정보에 의존하고 있지는 않은가?
- 모델의 최적화 목표가 **모든 사용자에게 공평하게 적용될 수 있는 목표**인가?
- 다양한 사용자 그룹에 대한 모델 성능을 검증하기 위해, **세분화된 평가**를 수행하고 있는가?
- ML 시스템이 **사용자의 삶에 어떤 영향**을 미치는지, **어떤 편향**을 가지는지 미리 파악하고 있는가?
- ML 모델의 훈련/평가에 대한 정보를 담은 **모델 카드**를 제공하고 있는가?
- Responsible AI 설계를 위한 **다양한 이해관계자가 접근**하기 쉬운 내부 도구가 있는가?
- Responsible AI에 관한 최신 정보를 파악하고 있는가?

**💡 Responsible AI를 단순히 조직의 규정 준수 요구 사항 충족을 위해 의무적으로 수행하는 일로 여기지 말자. ML 솔루션은 기술적인 것이지만, ML 시스템 설계는 기술 영역에 국한되지 않는다.**

> *Responsible AI를 단순히 조직의 규정 준수 요구 사항 충족을 위해 의무적으로 수행하는 일로 여기지 않기를 바랍니다*

**Q1. 일관성-정확도 트레이드오프가 해당 예시에서 왜 트레이드오프인가?**

A. 추천을 고정하면 사용자 경험의 일관성은 높아지지만, 그 사이에 더 좋은 추천이 가능해졌을 수 있으므로 정확도(최적의 추천)를 포기하게 된다. 반대로 매번 최신 모델로 예측하면 정확도는 높아질 수 있지만, 사용자 입장에서 "아까 봤던 결과가 달라졌다"는 혼란이 발생한다. 이 둘을 동시에 완벽히 만족시킬 수 없기에 트레이드오프라고 표현한다.
