## CHAPTER 10. MLOps를 위한 인프라와 도구

**한 줄 요약:** ML 시스템은 기술 문제가 아니라 인프라부터 사용자 경험까지 의사결정이 결합된 복합 시스템이며, 성공 여부는 이를 어떻게 설계하고 균형 잡느냐에 달려 있다 !

### 10.1 스토리지와 컴퓨팅

- **인프라의 4대 레이어**
    - 스토리지/컴퓨팅 → 자원 관리 → ML 플랫폼 → 개발 환경 순으로 구성됨. 회사 규모와 유스케이스 복잡도에 따라 필요한 레이어 수준이 다름.
    
    <img width="460" height="252" alt="Image" src="https://github.com/user-attachments/assets/ca14e73e-b5bb-4731-b4d5-ab73cc122a5c" />
    
- **컴퓨팅 레이어 핵심 개념**
    - 연산 유닛: CPU 스레드/코어부터 Spark 작업, Kubernetes 포드까지 추상화 수준이 다양함
    - 성능 지표: 메모리 크기(GB)와 FLOPS가 대표적이지만 FLOPS는 측정 기준이 회사마다 달라 신뢰도 낮음. 실제 MLPerf 벤치마크처럼 실제 워크로드 수행 시간으로 비교하는 게 현실적
    - 사용률(utilization): 이론 성능 대비 실제 성능 비율. 50%도 좋은 편으로 간주될 수 있음
    
    <img width="524" height="271" alt="Image" src="https://github.com/user-attachments/assets/ba2c9ef9-ff79-454d-b22d-bbad496ae522" />
    
- **퍼블릭 클라우드 vs. 프라이빗 데이터 센터**
    - 클라우드의 핵심 장점: 탄력적 확장, 초기 투자 불필요
    - 함정: 규모가 커질수록 클라우드 비용이 매출의 ~50%까지 차지할 수 있음. 드롭박스는 자체 데이터 센터로 이전해 2년간 7,500만 달러 절감
    - 현실적 대안: 클라우드로 시작 → 규모 커지면 하이브리드로 전환
    - 멀티클라우드: 전략적 선택이라기보단 조직 분리, M&A 등 우연히 발생하는 경우가 많음

### 10.2 개발 환경

- **왜 개발 환경이 중요한가**
    - 실제 현장에서 가장 과소평가되는 레이어. "인프라 한 부분만 구축할 시간이 있다면 개발 환경을 만들라"는 조언이 의미심장함.
- **IDE와 노트북**
    - 노트북의 강점: 상태 유지(stateful) → 대용량 데이터 반복 로딩 불필요, 중간부터 재시작 가능
    - 노트북의 함정: 셀 실행 순서가 보장되지 않아 재현성 확보가 어려움
    
    <img width="531" height="315" alt="Image" src="https://github.com/user-attachments/assets/d0d8eafa-acb6-4151-a7d0-d599b9ebada1" />
    
    - 보완 도구: 페이퍼밀(매개변수화된 반복 실험), 커뮤터(노트북 공유 허브), nbdev(문서+테스트 통합)
- **개발 환경 표준화의 중요성**
    - 패키지 버전, 파이썬 버전, 심지어 칩 아키텍처(M1 맥북 사례)까지 불일치하면 재현 불가 버그가 생김. 표준화는 requirements.txt의 버전 명시처럼 작은 습관에서 시작됨.
- **클라우드 개발 환경**
    - 로컬 개발의 한계(장비 의존성, 보안, 협업 어려움)를 해결하는 현실적 대안.
    - 비용: vCPU 4개/메모리 8GB 인스턴스가 시간당 $0.1 수준으로 엔지니어 시간 대비 충분히 저렴
    - 장점: IT 지원 단순화, 원격 접속, 보안 강화(도난 시 접근 권한 즉시 차단), 프로덕션 환경과의 간극 축소

> 💡 개발 환경 표준화는 편의의 문제가 아니라 팀 전체의 생산성과 직결! 작은 버전 불일치 하나가 며칠짜리 디버깅으로 이어질 수 있다는 게 공감된다.
> 
- **컨테이너: 개발 → 프로덕션 연결고리**
    - Dockerfile로 환경 재현 지침을 코드화 → 어떤 인스턴스에서도 동일한 환경 보장
    - 여러 컨테이너 관리: Docker Compose(단일 호스트) → Kubernetes(다중 호스트, 자동 확장)
    - K8s는 강력하지만 데이터 과학자 친화적이지 않음 → 이를 추상화하는 도구(쿠브플로 등)의 필요성이 대두됨

> 💡 컨테이너는 "내 컴퓨터에선 되는데"를 영구히 없애주는 기술!
>

### 10.3 자원 관리

- **클라우드 시대의 자원 관리 패러다임 전환**
- 과거: 유한한 자원을 최대한 쥐어짜는 것이 목표
- 현재: 비용 효율 + 엔지니어 생산성 극대화가 목표. 연산 자원을 더 쓰더라도 엔지니어 시간이 절약된다면 그게 이득이라는 인식이 보편화됨.
    - **크론 → 스케줄러 → 오케스트레이터 (진화 흐름)**
- ML 워크플로의 두 가지 핵심 특성인 반복성과 종속성을 얼마나 잘 다루느냐가 도구 선택의 기준.
    - 크론: 정해진 시간에 스크립트 실행. 종속성 처리 불가
    
    <img width="878" height="574" alt="Image" src="https://github.com/user-attachments/assets/a406b981-acf9-4616-a7a1-baa15f7c885c" />
    
    - 스케줄러: DAG 기반으로 종속성 처리. 작업 실패 시 재시도, 우선순위 대기열 관리, 자원 할당까지 담당
    - 오케스트레이터: "어디서" 자원을 가져올지 담당. 인스턴스 프로비저닝, 클러스터 관리 (ex. Kubernetes)
    - 실제로는 스케줄러가 오케스트레이터 위에서 실행되며 두 기능이 혼재하는 경우가 많음
    
    <img width="493" height="216" alt="Image" src="https://github.com/user-attachments/assets/bb65cdcb-e0a8-4039-a12e-1e60f8133688" />
    

> 💡 ML 워크플로가 단순 반복 실행이 아닌 조건부 종속성을 갖는 DAG라는 점을 이해하면, 왜 크론만으로는 부족한지가 보임!

- **데이터 과학 워크플로 관리 도구 비교**

| 도구 | 특징 | 단점 |
| --- | --- | --- |
| 에어플로 | 원조 오케스트레이터. 방대한 운영자 라이브러리 | 모놀리식(전체 워크플로우를 하나로 패키징), 매개변수 미지원, 정적 DAG |
| 프리펙트 | 에어플로 단점 보완. 동적 DAG, 매개변수 지원 | 컨테이너화가 우선순위 아님 |
| 아고 | 모든 단계가 자체 컨테이너에서 실행 | YAML 기반, K8s에서만 실행 가능 |
| 쿠브플로 | 아고 위에 구축. K8s 기반 | 상용구 코드가 여전히 많음 |
| 메타플로(추천!) | 로컬↔클라우드 전환이 매끄러움. 데코레이터로 요구사항 지정 | AWS 배치 또는 K8s 의존 |
- 메타플로의 핵심 강점: `@conda`로 환경 지정 → 컨테이너 자동 생성, `@batch` 추가 한 줄로 클라우드 전환. 개발/프로덕션 경계를 가장 자연스럽게 허문 도구.
    
    > 💡 에어플로가 먼저 나와서 시행착오를 다 겪어줬기 때문에 후발 도구들이 빠르게 개선될 수 있었다. 기술 생태계에서 "퍼스트 무버"가 항상 승자가 아님을 보여주는 사례다.
    > 
- (Deep Dive) Airflow의 "매개변수 미지원"에 대하여
    1. Airflow의 "매개변수" 문제가 뭔지
        1. **DAG 간 / Task 간 동적 파라미터 전달의 제약**
            - Airflow의 XCom은 task 간 데이터를 전달할 수 있지만, 본질적으로 메타데이터 DB에 직렬화해서 저장하는 구조라 대용량 데이터(모델 객체, 대형 DataFrame 등)를 넘기기엔 부적합
            - 그리고 DAG 실행 시점에 동적으로 파라미터를 바꿔서 실행하는 것도 `dag_run.conf`로 가능하긴 하지만, DAG 구조 자체를 동적으로 변경하는 건 제한적
        2. **DAG가 파싱 타임에 정적으로 결정된다는 구조적 한계**
            - Airflow는 DAG 파일을 주기적으로 파싱해서 구조를 확정하기 때문에, "이전 task 결과에 따라 다음 task의 파라미터 조합을 동적으로 생성"하는 게 직관적이지 않음
    2. "그냥 DAG에서 Optuna 돌리면 되는 거 아닌가?"에 대해
        - **되는 것**: 하나의 PythonOperator 안에서 Optuna study를 실행하고, 그 안에서 trial들이 알아서 돌아가는 건 문제없음 (Optuna가 자체적으로 파라미터 탐색을 관리하기 때문)
        - **안 되는 것 (혹은 어려운 것)**:
            - **Trial별 병렬화를 Airflow task로 분산하고 싶을 때**
                - Optuna의 각 trial을 별도 Airflow task로 만들어서 병렬 실행하려면, 파싱 타임에 몇 개의 trial을 돌릴지 미리 알아야 함.
                - Optuna의 pruning이나 adaptive sampling처럼 "이전 결과를 보고 다음 탐색을 결정"하는 로직과 Airflow의 정적 DAG 구조가 충돌
            - **리소스 격리가 필요할 때**
                - 예를 들어 LightGBM 튜닝은 CPU면 충분한데, 딥러닝 모델은 GPU가 필요하다면, trial마다 다른 인프라에서 실행하고 싶을 수 있음
                    
                    ➡️ 이걸 Airflow task 레벨에서 세밀하게 제어하기 어려움
                    
            - **장시간 튜닝의 내결함성**
                - 하나의 PythonOperator에서 100 trial을 돌리다가 87번째에서 OOM이 나면? 전체 task가 실패하고 처음부터 다시 돌아야 함
                - Trial별로 task를 나눴다면 실패한 것만 재시도할 수 있는데, 위의 동적 DAG 문제 때문에 이게 깔끔하지 않음
    
    ➡️ 만약 더 정교한 ML 파이프라인 오케스트레이션이 필요하다면, **Kubeflow Pipelines**, **Metaflow**, **ZenML** 같은 ML-native 오케스트레이터가 더 적합

### 10.4 머신러닝 플랫폼

- **왜 ML 플랫폼이 생겨났나**
    - 처음에는 한 팀이 특정 애플리케이션(추천 시스템 등)을 위해 도구를 개발함 → 다른 팀도 같은 도구가 필요하다는 걸 깨달음 → 공용 인프라로 분리해 ML 플랫폼 팀 탄생. 2020년 전후로 이 흐름이 본격화됨.
- **모델 배포**
    - 주요 클라우드 공급업체(SageMaker, Vertex AI, Azure ML)와 신생 도구(MLflow, Seldon, Ray Serve) 모두 제공.
    - 도구 선택 시 체크리스트: 온라인/배치 예측 모두 지원하는가, A/B 테스트·카나리 배포 같은 프로덕션 테스트가 쉬운가.
- **모델 스토어**
    - 단순히 S3에 모델 파일을 올리는 것만으로는 부족하다. 실제로 필요한 추적 아티팩트는 모델 정의, 모델 매개변수, 피처화 코드, 종속성, 학습 데이터, 생성 코드, 실험 결과, 태그까지 총 8가지.
    - 이 아티팩트들이 S3, ECR, Snowflake, W&B 등에 흩어져 있으면 디버깅할 때 "이 모델 누가 만들었지?"부터 시작하는 상황이 생김. 현재 가장 인기 있는 오픈 소스인 MLflow도 아티팩트 관리가 미흡해 스택오버플로 상위 질문의 절반이 이 주제.
    - 레퍼런스
        - MLflow : https://mlflow.org/docs/latest/index.html
        - DVC: https://dvc.org/doc
        - Weights & Biases : https://docs.wandb.ai/guides/artifacts

> 💡 모델 파일 하나를 배포하는 게 아니라 모델을 둘러싼 맥락 전체를 보존해야 한다는 관점이 중요하다. 담당자가 퇴사하거나 휴가를 간 순간 모델이 블랙박스가 되는 경험은 실무에서 매우 흔한 것 같음
> 
- **피처 스토어:** 세 가지 핵심 문제를 해결하는 도구
    - 피처 관리: 팀 간 피처 공유·검색. 피처 카탈로그 역할
    - 피처 연산: 연산 비용이 큰 피처를 한 번만 계산하고 재사용. 데이터 웨어하우스 역할
    - 피처 일관성: 훈련(배치)과 추론(스트리밍) 파이프라인의 피처 정의가 달라지는 문제 해결. 동일한 피처를 두 번 구현하는 낭비와 버그 위험 제거
    - 현황: 2022년 기준 피처 스토어 사용 회사 중 절반이 자체 개발. 아직 시장 표준이 없다는 신호.
    - 현재 가장 많이 쓰는 피쳐 스토어 오픈소스
      - Feast 공식 문서: https://docs.feast.dev/
        

> 피처 일관성 문제는 이전에 공부했었던 학습-서빙 스큐(training-serving skew)와 직결된다. 같은 피처를 두 언어로 두 번 구현하는 것 자체가 이미 버그를 초대하는 구조라는 점에서, 피처 스토어의 필요성이 단순한 편의가 아닌 신뢰성의 문제임을 알 수 있음

### 10.5 구축 VS 구매

- ML 인프라를 직접 구축(Build)할 것인지, 외부 솔루션을 구매(Buy)할 것인지에 대한 전략적 의사결정
- 단순한 기술 선택이 아니라 비용 구조, 조직 구조, 장기 혁신 속도에 영향을 미치는 경영 의사결정
- 보편적인 3가지 검토 사항
    - 회사가 속하는 성장 단계: 초기 팀이면 구매, 아니라면 구축도 고려 가능
    - 회사의 주안점 또는 경쟁 우위라고 생각하는 것: 사내에서 정말 잘하고 싶으면 구축을, 그렇지 않으면 구매를 할 것임
    - 사용 가능한 도구의 성숙도: 구매하려는 인프라가 우리 서비스와 얼마나 잘 맞는가

**Q. 컴퓨팅 연산에서 사용률 50%도 좋은 편이라고 했는데 어떤 요인 때문에 100%에 못 미치는 건가?**

- A1: **데이터 공급의 병목 (Memory Wall):** 연산 장치(GPU/CPU)의 속도는 매우 빠르지만, 메모리나 저장장치에서 데이터를 가져오는 속도가 이를 받쳐주지 못해 장치가 노는 '대기 시간'이 발생
- A2: **구조적 오버헤드 및 병렬성 한계:** 작업을 배분하는 스케줄링 비용, 장치 간 통신 지연, 너무 작은 배치 사이즈나 잘게 쪼개진 연산 단위 때문에 자원을 풀 가동하기 위한 충분한 일감을 확보하기 어려움
- A3: **안정성과 성능의 트레이드오프:** 사용률이 100%에 가까워지면 응답 시간(Latency)이 급증하고 발열로 인한 성능 저하(Throttling)가 발생하므로, 실무에서는 효율과 안정성을 위해 50~80% 수준을 황금 밸런스로 취급

**Q. 스케줄러가 작업에 필요한 자원을 사용자가 잘못 지정해도 실제 필요량을 추정해 회수한다고 했는데, 이런 자원 추정은 어떻게 가능한 건가? 과거 실행 이력을 학습하는 건가?**

A. (Claude) Borg 논문에 따르면 실제로 과거 실행 이력(task resource usage history)을 바탕으로 한 휴리스틱 추정과 실행 중 실제 사용량 모니터링을 병행합니다. 오버커밋(overcommit) 전략으로 선언된 자원보다 더 많은 작업을 스케줄링하되, 실제 사용량이 한계에 달하면 우선순위 낮은 작업을 선점(preempt)하는 방식입니다.

- Borg 논문
  - 실제 사용량 추적 기반 점진적 보정 + 오버커밋 + 우선순위 선점
    - [Large-scale cluster management at Google with Borg](https://research.google/pubs/large-scale-cluster-management-at-google-with-borg/)

**Q. 피처 일관성 문제를 해결하려고 훈련/추론 피처 로직을 통합한다고 했는데, 훈련은 배치로 처리하고 추론은 실시간으로 처리하는 상황에서 동일한 로직을 어떻게 두 방식에 동시에 적용하는 건가?**

A. (Claude) Feast의 구조가 이 질문의 가장 명확한 답입니다. 피처 정의(Feature View)를 한 번만 작성하면, 오프라인 스토어(배치 훈련용)와 온라인 스토어(실시간 추론용)에 동일한 정의를 적용해 각각 물질화(materialization)합니다. 로직 자체는 하나이고, 실행 환경만 다른 셈입니다.
