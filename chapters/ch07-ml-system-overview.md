## CHAPTER 7. 모델 배포와 예측 서빙

> 한 문장: 프로덕션 ML은 단일 모델을 한 번 배포하는 것이 아니라 수천 개의 모델을 업데이트하면서 밀리초 단위 레이턴시로 수백만 사용자에게 서빙하는 스케일의 문제!
> 

---

- **배포(deploy)**: 모델을 실행하고 액세스 가능하게 함
- 개발 환경 → 스테이징 환경 (테스트용) → 프로덕션 환경 (최종 사용자용)
- **배포 (쉬운 부분)**
    - FastAPI나 Flask로 POST 요청 엔드포인트로 예측 함수를 래핑
    - 필요한 종속성 패키지들을 컨테이너에 배치
    - AWS나 GCP 같은 클라우드 서비스에 푸시해 엔드포인트 노출
        
        ```python
        # FastAPI를 사용해 예측 함수를
        # POST 엔드포인트로 변환하는 예시
        @app.post("/predict")
        async def predict(data: dict):
            X = data['X']
            y = MODEL.predict(X).tolist()
            return {"y": y}
        
        ```
        

- **배포 (어려운 부분)**
    - 사용자 수백만 명이 밀리초 단위 레이턴시와 99% 가동 시간으로 모델을 사용하도록 함
    - 문제 발생 시 적절한 사람에게 즉시 알리도록 인프라 설정
    - 잘못된 부분을 파악하고 문제를 수정하기 위해 업데이트를 원활하게 배포

> **Note. 모델 내보내기 (= 직렬화, Serialization)**
모델을 다른 애플리케이션에서 사용할 수 있는 형식으로 변환
- **모델 정의**: 히든 레이어 개수와 각 레이어의 유닛 개수 같은 모델 구조
- **모델 매개변수값**: 이러한 유닛과 레이어에 대한 값
TensorFlow: `tf.keras.Model.save()` → SavedModel 형식
PyTorch: `torch.onnx.export()` → ONNX 형식
> 

<aside>
💡 프로토타입 배포와 프로덕션 배포는 완전히 다른 부분이다. 진짜 도전은 규모와 안정성에 있다.

</aside>

### 7.1 머신러닝 배포에 대한 통념

**7.1.1 통념 1: 한 번에 한두 가지 머신러닝 모델만 배포합니다.**

- **학계의 관점**
    - 학술 프로젝트: 작은 문제를 선택해 집중 → 단일 모델 배포로 이어짐
    - 학계 사람들은 ML 프로덕션을 단일 모델 맥락에서 생각하는 경향
    - 결과: 한두 가지 모델만 지원하는 인프라 → 실제 애플리케이션에는 작동하지 않음

**기업의 현실**

- 실제 애플리케이션: 다양한 기능 → 각 기능에는 자체 모델 필요

<img width="622" height="406" alt="Image" src="https://github.com/user-attachments/assets/364063e6-fd30-4163-8f0f-a406004afbab" />

**💡 모델 하나만 잘 만들면 되겠지라는 생각 <<< 실제 기업에서는 수백, 수천 개의 모델을 관리해야 하므로, 확장 가능한 인프라와 자동화가 필수!**


---

**7.1.2 통념 2: 아무것도 하지 않으면 모델 성능은 변하지 않습니다** 

- **소프트웨어 부패 (Software Rot / Bit Rot)**
    - 시간에 따라 소프트웨어 프로그램이 아무런 변화가 없어 보임에도 성능이 저하되는 현상
- **ML 시스템의 특수한 문제: 데이터 분포 시프트**
    - **데이터 분포 시프트(Data Distribution Shift)**: 프로덕션에서 모델이 접하는 데이터 분포가 훈련된 데이터 분포와 다를 때 발생
    - **ML 모델은 훈련 직후에 가장 잘 수행되고 점점 성능이 저하되는 경향**

<aside>
💡 ML 모델은 만들어두면 끝이 아니다. 시간이 지나면서 모델은 점점 현실과 동떨어진다. 지속적인 모니터링과 재학습이 필수!

</aside>

---

**7.1.3 통념 3: 모델을 자주 업데이트할 필요 없습니다.**

- **모델 업데이트의 중요성**
    - 모델 성능은 시간에 따라 저하되므로 **최대한 빨리 업데이트해야 함**
    - **현재의 업데이트 빈도**
    - 많은 회사: 한 달에 한 번 또는 분기에 한 번 (여전히 느림)
    - **웨이보**: 일부 ML 모델을 **10분마다** 업데이트

<aside>
💡 선도 기업들은 10분마다 모델을 업데이트한다. 빠른 업데이트 = 빠른 학습 = 경쟁 우위.

</aside>

---

**7.1.4 통념 4: 대부분의 머신러닝 엔지니어는 스케일에 신경 쓰지 않아도 됩니다.**

- **'스케일'의 의미**
    - 초당 수백 개의 쿼리를 처리
    - 한 달에 수백만 명의 사용자를 처리

<aside>
💡 머신러닝 엔지니어는 100명 이상 회사에서 일할 확률이 50% 이상이고, 그런 회사는 대부분 스케일(규모)의 문제를 다룬다.

</aside>

### 7.2 배치 예측 vs 온라인 예측

- **예측 생성 및 서빙 방법의 중요성:** 최종 사용자와 시스템에서 작업하는 개발자 모두에게 영향을 미침
- **기억해야 할 세 가지 주요 예측 모드**
    1. 배치 피처만 사용하는 배치 예측
    2. 배치 피처만 사용하는 온라인 예측 (예: 사전 계산된 임베딩)
    3. 배치 피처와 스트리밍 피처를 모두 사용하는 온라인 예측 (스트리밍 예측이라고도 함)
- **온라인 예측**(= on-demand 예측 = 동기(synchronous) 예측)
    - **정의:** 예측에 대한 요청이 도착하는 즉시 예측이 생성되고 반환되는 경우
    
    <img width="1064" height="508" alt="Image" src="https://github.com/user-attachments/assets/1982d3b8-f37c-4e1f-9bd7-d4771cad1b4c" />
    
    - **특징**
        - RESTful API를 통해 요청이 예측 서비스로 전송됨 (예: HTTP 요청)
        - 예측 요청이 HTTP 요청을 통해 전송될 때 온라인 예측은 요청과 동기식으로 생성됨
    - **예시:** 구글 번역 / 영어 문장을 입력하는 즉시 프랑스어 번역문이 돌아옴
- **배치 예측** (= 비동기(asynchronous) 예측이라고도 함)
    - **정의:** 예측이 주기적으로 혹은 트리거될 때마다 생성되는 경우, 필요에 따라 검색
        - 예측 결과는 SQL 테이블이나 인메모리 데이터베이스 같은 곳에 저장
    
    <img width="1080" height="356" alt="Image" src="https://github.com/user-attachments/assets/735669b5-f926-48ea-9682-0ea4afee14eb" />
    
    - **특징:** 요청과 비동기식(Asynchronous)으로 생성됨
    - **예시**
        - 넷플릭스: 네 시간마다 모든 사용자에 대한 영화 추천을 생성
        - 사용자가 넷플릭스에 로그인할 때 사전 계산된 추천을 가져와서 표시

**배치 피처 vs 스트리밍 피처**

- **배치 피처**
    - 데이터베이스나 데이터 웨어하우스의 데이터 같은 **과거 데이터**에서 계산된 피처
    - 배치 예측: 배치 피처만 사용
- **스트리밍 피처**
    - **스트리밍 데이터**(실시간 전송 데이터)에서 계산된 피처
    - 온라인 예측: 배치 피처와 스트리밍 피처를 모두 사용 가능

<img width="593" height="340" alt="Image" src="https://github.com/user-attachments/assets/ccd81243-5cc6-4679-bffe-46887836cd34" />

- **온라인 예측 vs 배치 예측 비교**

<img width="672" height="201" alt="Image" src="https://github.com/user-attachments/assets/104a2d59-63ee-4649-99c2-1377107c02bb" />

- **효율성에 대한 오해**
    - 많은 사람들은 온라인 예측이 배치 예측보다 비용과 성능 면에서 비효율적
    - 이유: 입력을 배치 처리하지 못하고 벡터화나 기타 최적화 기술을 활용할 수 없음
    - **온라인 예측의 장점**: 사이트를 방문하지 않는 사용자에 대해 예측을 생성할 필요가 없음
        - e.g., Grubhun 사용자는 3,100만 명이었지만, 일일 주문 건수는 약 62만 건에 불과함
            
            ➡️ 즉, 배치 예측을 수행했다면 98%의 연산은 낭비임
            

<aside>
💡 배치 vs 온라인은 어느 것이 더 좋은가가 아니라 언제 어떤 것을 쓰는가의 문제다. 실시간 개인화가 중요하면 온라인, 대량 처리가 효율적이면 배치. 많은 프로덕션에서 두 방식을 혼합해 사용한다.

</aside>

**7.2.1 배치 예측에서 온라인 예측으로** 

- **온라인 예측의 문제점: 모델이 예측을 생성하는 데 너무 오래 걸릴 수 있음**
- **배치 예측이 유용한 경우**
    - 온라인 예측이 충분히 저렴하지 않거나 충분히 빠르지 않을 때
    - 비용과 속도가 동일하면서 필요에 따라 예측을 생성할 수 있다면, 굳이 예측을 백만 개씩 미리 생성하면서 저장과 검색에 공들일 필요 없음
- **배치 예측 모델의 단점:**
    1. 최신의 트렌드에 덜 민감함
    2. 텍스트 번역처럼, 현실적으로 모든 처리를 미리 해둘 수 없는 경우에 적합하지 않음
- **배치 예측이 유리한 경우:**
    1. 온라인 예측이 충분히 **저렴하지 않은** 경우
    2. 온라인 예측이 충분히 **빠르지 않은** 경우
    
    ➡️ 점점 더 하드웨어의 기술이 발전함에 따라 저렴하고 빠른 온라인 예측이 가능해지고 있음
    

<aside>
💡 배치 예측은 느린 모델의 레이턴시를 숨기는 트릭으로 시작했지만, 결국 온라인 예측이 필요하다.

하드웨어와 알고리즘의 발전으로 실시간 개인화가 가능해지고 있고, 선도 기업들은 이미 그 방향으로 전환 중이다.

다만 모든 경우에 온라인이 답은 아니며, 하이브리드 접근이 현명할 때도 많다!

</aside>

**7.2.2 배치 파이프라인과 스트리밍 파이프라인의 통합**
  - Train과 Inference에 서로 다른 파이프라인이 있는 것은 ML 프로덕션에서 버그가 발생하는 일반적인 원인임
      
      <img width="1248" height="564" alt="Image" src="https://github.com/user-attachments/assets/e9d3e1dc-cfc1-42ea-856c-aa2537d50666" />

      
      e.g., **모델링 팀은 모델 Train을 위해 배치** 파이프라인을, **배포 팀은 모델 Inference를 위해 스트림** 파이프라인을 유지보수하는 경우
      
  - 스트림 처리와 배치 처리 통합을 위한 인프라 구축은 매우 중요한 주제임
      1. 실제로 우버, 웨이보와 같은 기업들에서도 Apache Flink를 통해 배치/스트림 파이프라인을 통합을 위해 주요 인프라를 정비함
          - *Apache Flink: 실시간 스트림 데이터 처리와 배치 처리를 모두 지원하는 오픈소스 분산 처리 프레임워크 스트림 프로세서*
      2. 일부 기업은 피처 스토어를 사용해, ‘Train에 사용되는 배치 피처’와 ‘Inference에 사용되는 스트리밍 피처’의 **일관성을 보장**하기도 함

### **7.3** 모델 압축

> 배포할 모델이 **예측값을 생성해 내는 데에 시간이 너무 오래 걸릴 때**에 유용
> 
- **추론 레이턴시를 줄이는 3가지 접근법**
    1. 추론을 더 빠르게 하기 (추론 최적화)
    2. 모델을 더 작게 만들기 (모델 압축)
    3. 배포된 하드웨어의 성능을 높이기

- **가장 대중적인 모델 압축의 4가지 유형**
    1. 저차원 인수분해 (e.g., SqueezeNet, MobileNet)
        - SqueezeNet
            
            > 3x3 합성곱을 적용해야 할 자리에, 1x1 합성곱을 사용
            > 
            > 
            > ➡️ 데이터를 훨씬 작은 차원으로 보내서 추론 속도를 ↑
            > 
        - MobileNet
            
            > 하나의 큰 합성곱 연산을 공간(Depthwise) 따로, 채널(Pointwise) 따로 두 단계로 쪼개서 수행
            > 
            > 
            > ➡️ 정확도는 거의 그대로 유지하면서, 연산량과 파라미터 수를 일반 모델 대비 10% 수준으로 감소
            > 
        
        ---
        
    2. 지식 증류
        
        > 이미 잘 학습된 거대한 모델(Teacher)의 지식을 상대적으로 가벼운 모델(Student)에게 전수하는 방식
        > 
        - 작은 모델이 단순히 정답(0 또는 1)만 맞히는 것이 아니라, 
        큰 모델이 출력하는 확률 분포(예: 개 80%, 고양이 15%, 호랑이 5%)를 그대로 흉내 내도록 학습시켜 크기 대비 높은 성능을 내게 만듦
    3. 가지치기
        
        > 신경망의 가중치 중에서 모델의 결과에 큰 영향을 주지 않는 중요도가 낮은 연결(Weight)이나 뉴런을 제거하는 기술
        > 
    4. 양자화
        
        > 가중치나 활성화 값을 표현하는 숫자의 정밀도를 낮추는 기법
        > 
        > - 보통 32비트 부동소수점(FP32)으로 표현된 숫자를 8비트 정수(INT8)나 그 이하로 변환

### 7.4 클라우드와 에지에서의 머신러닝

- 모델 계산을 어디서 해야 하는가: 클라우드 vs 에지
    - 클라우드에서 수행 시 클라우드에서 많은 계산이 수행됨
    - 에지에서 수행 시 소비자 디바이스(브라우저, 휴대전화, 노트북, 스마트워치, FPGA, ASIC, 로봇 등)에서 많은 계산이 수행됨
- 클라우드 배포의 경우 **비용**이 너무 많이 듦
    - 2018년에 대기업은 매년 수억 달러, 중소기업은 매년 5만~200만 달러를 지출함
    - 스타트업은 잘못하면 파산할 수도 있음 !
    
    → 그렇기에 **에지 컴퓨팅에 대한 수요**가 늘어가고 있음
    
- 에지 컴퓨팅의 장점
    1. **클라우드 컴퓨팅이 불가능한 곳에서 앱을 실행할 수 있음**: 인터넷망이 잘 안깔려 있는 곳에서도 문제 없이 작동 가능함
    2. **네트워크 레이턴시에 대한 우려가 줄어듦**: 네트워크는 사용자의 위치와 서비스에 따라 최대 몇 초까지도 소요될 수 있음
    3. **민감한 사용자 데이터를 처리하기에도 용이함**: 항상 안전한 것은 아니지만 네트워크 통해서 하는 것보단 나음
- 에지 컴퓨팅을 하려면
    1. 에지 디바이스가 계산 처리 가능할 정도로 강력해야 함
    2. ML 모델을 저장할 충분한 메모리가 있어야 함
    3. 배터리가 충분하거나 적절한 시간 동안 애플리케이션에 전원을 공급할 에너지원이 있어야 함
- 2025년에 300억 개의 활성화된 에지 디바이스가 있을 것으로 예상했고, 대략 **210억 개가 존재**

**7.4.1 에지 디바이스용 모델 컴파일 및 최적화**

- 사용자 코드 → ML 프레임워크 → 하드웨어 백엔드 → 실제 하드웨어의 구조를 지님
- 모델은 프레임워크로 개발되지만, 실제 실행은 하드웨어가 하므로, 그 하드웨어가 해당 프레임워크를 실행할 수 있도록 프레임워크를 이해할 수 있어야 함
    
    = 프레임워크 연산을 GPU/TPU 구조에 맞게 번역해서 실행할 수 있어야 함
    
    → 2018년엔 TPU가 처음 공개되었지만 파이토치는 2020년 9월에서야 지원됐던 적이 있음
    
- 신규 하드웨어에 ML 모델을 배포하려면 **상당한 수작업을 필요로 해서** 어려움
    
    → 모든 신규 플랫폼에 탑재하도록 직접 개발하는 것보다, 프레임워크와 플랫폼을 연결할 ‘중개자’를 만들면 어떨까? = 중간 표현(IR)
    
- 중간 표현(IR): 컴파일러 작동 방식의 핵심으로, 모델의 원래 코드에서 하드웨어 백엔드에 네이티브 코드를 생성하기 전에 일련의 고수준 및 저수준 IR을 생성함
    
    <img width="1142" height="606" alt="Image" src="https://github.com/user-attachments/assets/8b47f7cc-fc9e-480c-acfe-3dff4f48e167" />
    
- 모델 최적화의 필요성: 프레임워크 내 개별 함수는 최적화돼도, 프레임워크 전반에 걸친 최적화는 전무할 수 있음
    - 최적화 컴파일러: 코드까지 최적화하는 컴파일러. ML 모델 코드를 기계 코드로 낮추는 과정에서 ML 모델의 **계산 그래프와 모델 구성 연산자를 보고 속도 높일 방안을 찾아냄**
- 로컬 최적화: 모델의 연산자 또는 연산자 집합을 최적화
    - 벡터화(Vectorization): 루프를 한 번에 여러 데이터에 적용함으로써 메모리 I/O 지연을 줄임
    - 병렬화(Parallelization): 입력 데이터를 독립적인 청크로 나눠 동시에 실행함
    - 루프 타일링(Loop tiling): 루프에서 데이터 접근 순서를 바꿔 캐시 효율을 높임
    - 연산자 융합(Operator fusion): 여러 연산을 하나의 연산으로 합쳐 중복 메모리 접근을 제거함
- 전역 최적화: 전체 계산 그래프를 엔드-투-엔드로 최적화
    - 그래프 수준 최적화: 단순 연산자 최적화보다 **계산 그래프 구조 자체**를 활용한 최적화가 더 큰 효과를 냄
    - 합성곱 신경망에서는 **수직 융합** (Conv + Bias + ReLU), **수평 융합** (여러 레이어 병합)을 통해 메모리 접근을 크게 줄일 수 있음
- 휴리스틱 기반 최적화의 한계
    - 비최적(non-optional): 최선이라는 보장이 없음
    - 비적응적(non-adaptive): 새 하드웨어, 모델마다 다시 설계해야 함
    - 특정 인기 모델에만 과도하게 최적화되는 경우도 있음
- 계산 그래프를 실행하는 경로 탐색 자체를 ML로 최적화할 수도 있음 (모든 실행 경로 탐색하기는 불가능하기 때문에)
- autoTVM: 실제 실행 시간을 측정해, 주어진 하드웨어에서 가장 빠른 실행 방법을 자동으로 찾는 ML 기반 컴파일러 최적화 도구
    - 실행 경로가 너무 많아 수작업 최적화가 어려움
    - 후보 경로를 실제로 실행해 시간을 잼
    - 그 결과로 비용 모델을 학습함
    - 빠른 경로만 골라 전체 그래프를 구성함
    - 결과는 인상적이지만 속도는 느림. 다만 일회성이니 한 번만 잘 실행해두면 ..! 좋음

**7.4.2 브라우저에서의 머신러닝**

- 브라우저에서 모델을 실행하면 **하드웨어 종류와 무관하게 실행 가능함**
- JavaScript 기반 접근
    - TensorFlow.js 등 사용함
    - 구현은 쉬우나 성능이 느림
    - 복잡한 로직에 제약이 있음
- WebAssembly(WASM) 기반 접근
    - 다양한 언어로 작성된 모델을 브라우저에서 실행 가능하게 함
    - JavaScript보다 훨씬 빠름
    - 대부분의 기기에서 지원됨
    - 실행 속도가 느리다는 단점이 있음

**Q2. 모델을 10분마다 업데이트한다는 것이 현실적으로 가능한가요? 재훈련 시간은 어떻게 관리하나요?**

A. 10분마다 업데이트는 "전체 모델을 처음부터 재훈련"이 아니라 "증분 학습(Incremental Learning)" 또는 "온라인 학습(Online Learning)"을 의미할 가능성이 높습니다. 또는 사전 훈련된 모델의 마지막 레이어만 미세 조정하거나, 앙상블 모델 중 일부만 업데이트하는 방식일 수 있습니다. 추가로 A/B 테스팅 인프라를 통해 새 모델을 점진적으로 롤아웃하면서 안정성을 확보하는 것도 중요합니다.

**Q3. 스트리밍 피처와 배치 피처를 동시에 사용할 때 피처 엔지니어링의 일관성은 어떻게 보장하나요?**

A. **피처 스토어**를 도입해 학습용(Offline)과 서빙용(Online) 데이터의 정의를 하나로 통합하고 관리 (가장 표준적인 해결책)

- 그 외의 방법
    - **통합 처리 엔진**(Flink 등)을 사용해 배치와 스트리밍 데이터에 대해 완전히 동일한 계산 로직을 적용
    - **서빙 시점의 로그**를 남겨 실제 예측에 사용된 피처값을 나중에 학습 데이터와 비교하며 일관성을 지속적으로 검증
