## CHAPTER 9. 연속 학습과 프로덕션 테스트

> **좋은 시스템이 반드시 유용한 것은 아니며, 나쁜 시스템이 반드시 유용하지 않은 것도 아니다.**

### 9.1 연속 학습

- 핵심 교훈: 연속 학습은 알고리즘보다 인프라 문제에 가까움
- 그렇기에 연속 학습을 무분별하게 적용하면 여러 문제가 발생할 수 있음
- 연속 학습 시 주의점
  - **1. 모든 신규 샘플을 바로 모델 업데이트에 사용하면 안 됨**
    - (1)Catastrophic forgetting: 신경망이 새로운 정보를 학습할 때, 과거에 학습한 정보를 급격히 잊어버리는 경향
    - (2) 높은 훈련 비용: 다수의 하드웨어는 대부분 배치 처리를 위해 설계되어 있어서 비효율적
    - 
      ➡️ 대다수의 기업이 데이터 포인트 512, 1024개마다 모델을 업데이트 함

  
  - **2. 업데이트된 모델은 평가가 완료될 때까지 배포하면 안 됨**
    - ➡️ champion 모델과 challenger 모델을 비교 평가 후 배포

  - **3. 모델을 ‘자주’ 업데이트할 필요가 없음**
  - 이유: 충분한 신규 데이터가 자주 발생하지 않고, 모델 성능은 빠르게 하락하지 않음

#### 9.1.1 무상태 재훈련 vs. 상태 유지 훈련

- **용어 정의**
    - **Stateless Retraining (무상태 재훈련):** 모델을 맨 처음부터 재훈련
    - **Staeful Retraining (상태 유지 훈련):** 모델을 신규 데이터만 추가해서 추가 훈련
        
        > Fine-tuning 또는 Incremental Training이라고도 함
        > 
    - Stateless Retraining과 Staeful Retraining의 차이
        
        <img width="487" height="302" alt="image" src="https://github.com/user-attachments/assets/1a2de243-4aec-4fe6-ae4c-a8cb4972391b" />

        
- **Staeful Retraining**
    - **장점:** 데이터를 계속 저장해두어야 하는 일을 피할 수 있음
        
        ➡️ 개인 정보 보호 요구사항이 엄격한 경우 유리
        
    - 하지만, 모델을 교정하기 위해, 모델을 처음부터 재학습시키는 경우도 종종 있다
    - **2가지 모델 업데이트 유형**
        
        
        | 모델 업데이트 유형 / 요소 | 모델 아키텍처 | 피처 | 데이터 |
        | --- | --- | --- | --- |
        | Model Iteration(모델 반복) | 변경 | 변경 |  |
        | Data Iteration(데이터 반복) |  |  | 변경 |
        
        ➡️ 대부분이 Data Iteration !
        
- **필자의 용어 정리:**
    1. ‘온라인 학습’ X ➡️  **‘연속 학습’ 🙆🏻‍♂️**
        - 이유: 이렇게 검색하면 온라인 강의가 나와서
    2. ‘Continuous Learning’ X ➡️  **‘Continual Learning’ 🙆🏻‍♂️**
        - 이유:
            1. Continuous Learning은 DevOps 관점
                
                → ML 모델의 무중단 배포(CD)를 지칭하기 위해 쓰이는 경우가 종종 있어서 헷갈림
                
            2. Continual Learning은 ML 관점

**9.1.2 Continual Learning의 필요성**

- Continual Learning이 필요한 경우
    1. 데이터 분포 시프트가 생기는 경우
    2. 희귀한 사건에 적응하기 위함
        
        > 블랙 프라이데이처럼 갑작스럽게 수요가 급등하는 경우, 고객 행동을 정확하게 예측할 수 없음
        > 
        > 
        > → 학습 주기를 빠르게 해서, 하루 종일 신규 데이터로 모델 업데이트를 해야 함
        > 
    3. 콜드 스타트 문제
        
        > 신규 사용자에 대한 과거 데이터 없이, 예측을 해야하는 경우
        > 
        > 
        > → 빠르게 모델을 학습해서 사용자의 만족도를 높여야 함
        > 
- Continual Learning >> Batch Learning
    - 전통적인 Batch Learning이 할 수 있는 모든 것을 Continual Learning이 할 수 있음
        
        ➡️ Continual Learning 세팅 및 수행에 드는 인풋이 Batch Learning과 동일한 수준이라면, Batch Learning을 선택할 이유가 전혀 없음
        
        하지만, Continual Learning은 아직까지 많은 어려움이 있음

**9.1.3 Continual Learning의 난제**

- Continual Learning의 3가지 주요 난제
    1. 신규 데이터 액세스
        
        > 데이터 소스가 많을수록, 데이터 적재 파이프라인이 길면 길수록, 
        모델 학습을 위한 데이터를 액세스하는 데에 오랜 시간이 걸림
        > 
        
        ➡️ DW에 저장되기 전에 바로 액세스 받는 방식 등으로 해결
                
        - 데이터 내에 레이블링이 필요한 경우, 레이블링 속도로 인해 신규 데이터 액세스가 어려워지기도 함
            - 따라서, Continual Learning에 가장 적합한 태스크는 **자연 레이블**을 얻을 수 있는 태스크임
            - 또는 레이블링 프로세스를 개선하기도 함
                - 해결 1: 프로그래밍 방식 레이블링 툴 사용
                    
                    > 사람의 개입을 최소화하여 작업속도를 늘리는 방식
                    > 
                    > - e.g., Snorkel(스노클)
                - 해결 2: 크라우드소싱된 레이블을 활용
                    
                    > 사람 자체를 늘려버리는 방식 (레이블링 아르바이트 많이 구하기)
                    > 
    2. 평가
        - 모델 업데이트를 자주할 수록, 모델 평가도 자주해야 함
            
            ➡️ 모델을 자주 업데이트할 수록, 모델이 실패할 수 있는 확률도 높아짐
            
            ➡️ 업데이트 모델 평가도 또하나의 병목 현상임 (e.g., A/B 테스트를 위한 충분한 샘플 수 확보 등)
            
        - Adversarial Attack(적대적 공격)에 약함
            - e.g., 2016년 MS에서 공개한 챗봇 Tay가 인종 차별적 발언을 학습한 사례
    3. 알고리즘
        
        > **미리 알고 넘어갈 것:**
        > 
        > - 신경망 기반 모델 ↔ 행렬 기반 모델 `공부 더 필요`
        >     1. 신경망 = 신경망 기반 모델
        >     2. 협업 필터링(Collaborative Filtering) = 행렬 기반 모델
        > - Continual Learning에는 ‘행렬 기반’, ‘트리 기반’ 모델보다 ‘신경망 기반’ 모델이 더 적합
        - 알고리즘 난제 예시
            - 협업 필터링 모델 업데이트를 위해서는 전체 데이터셋을 통한 User-Item 행렬을 구축하고 차원 축소 수행해야 함 (시간이 많이 소요)
                
                ➡️ Continual Learning에 부적합
                
                - ↔ 신경망 모델은 임의 크기의 데이터 배치로 모델 업데이트 가능 (극단적으로는 단 1개의 샘플로도 업데이트 가능)
                    
                    ➡️ Continual Learning에 적합

**9.1.4 Continual Learning의 네 단계**

> 기업의 ML 도입에 따른 성장 과정 느낌
> 
- **Step 1: 수동 Stateless Retraining(무상태 훈련)**
    
    > ML 신규 모델 개발에만 집중하는 단계 (모델 업데이트에 대한 고민은 아직 X)
    > 
    - ML 도입 3년 미만의 대다수의 기업들이 이 단계에 있음
- **Step 2: 자동 재훈련**
    
    > 신규 모델 개발보다는 기존 모델 유지/개선에 집중하는 단계
    > 
    > - Spark와 같은 배치 프로세스를 통해 모델 재훈련을 주기 실행
    - 모델 자동 재훈련을 위해서는 스크립트를 작성해야 함
        - 자동 업데이트 스크립트의 주요 3요소
            1. 스케쥴러 (e.g., Airflow, Ago)
            2. 데이터의 가용성과 접근성
            3. 모델 스토어 (e.g., S3, MLflow)
                - *S3는 모델을 적재하기에 좋지는 않다 (사람이 읽을 수 없기 때문)*
                    
                    ➡️ AWS의 SageMaker 또는 MLflow가 더 적합
                    
- **Step 3: 자동 Stateful Retraining**
    - Step 2에서 작성한 모델 자동 재훈련을 위한 스크립트에 **모델 업데이트를 어디서부터 수행할지를 담은 ‘체크포인트’만 추가**하면 됨
    - 이 단계에서 주의를 기울여야하는 점
        - Data Lineage, Model Lineage를 잘 관리하기
            - Data Lineage 예시
                
                ```sql
                -- stg_users
                -- 원천 데이터(raw_users)에서 데이터를 가져옴
                SELECT 
                    id, 
                    signup_date,
                    country
                FROM {{ source('main_db', 'raw_users') }}
                ```
                
                ```sql
                -- 위에서 만든 stg_users를 참조함 (Lineage 형성)
                SELECT 
                    country, 
                    count(*) as user_count
                FROM {{ ref('stg_users') }}
                WHERE signup_date >= '2024-01-01'
                GROUP BY 1
                ```
                
            - Model Lineage 예시
                
                ```yaml
                stages:
                  train:
                    cmd: python train.py --epochs 10 --lr 0.01  # 실행 명령
                    deps:
                      - data/processed_data.csv               # 데이터 의존성 (Data Lineage와 연결)
                      - src/train.py                          # 코드 의존성
                    params:
                      - train.learning_rate                   # 하이퍼파라미터 ($Learning Rate$)
                    outs:
                      - models/model_v1.pkl                   # 결과물 (Model Artifact)
                ```
                
- **Step 4: Continual Learning 🌟**
    
    > Step 3에서 Step 4로 넘어오는 과정이 험난하다
    > 
    - 모델 업데이트 주기를 결정하는 방식
        1. 업데이트 주기를 결정 (시간 기반)
        2. 데이터 분포가 변할 때 (드리프트 기반)
        3. 모델 성능이 하락할 때 (성능 기반)
        4. 레이블링된 데이터 총량이 n% 증가할 때 (볼륨 기반)

**9.1.5 모델 업데이트 빈도**

- “모델을 얼마나 자주 업데이트해야 하는가?”라는 질문에 답하기 전에 아래의 질문에 먼저 답해야 한다
    
    ➡️ 모델을 업데이트했을 때, 성능이 얼마나 향상 되는가
    
    ➡️ 모델 업데이트 빈도를 변경했을 때, 성능이 얼마나 향상 되는가 (e.g., 매월/매주/매일)
    
    - 2014년 페이스북은 광고 클릭률 예측 모델에 대해, 주간 재훈련에서 일일 재훈련으로 전환했을 때 모델 손실 1%가 감소한다는 사실을 발견
        - 즉, 최근 컨텐츠나 사용자의 관심처럼 빠르게 변화하는 데이터의 경우, 신규 데이터의 가치가 보다 높음
- Model Iteration과 Data Iteration
    - 이론상 모델 업데이트를 위해 2가지 Iteration을 모두 수행할 수 있으나, 인풋 대비 아웃풋을 고려해서 결정해야 함
        - e.g., 최근 데이터를 빠르게 새로 업데이트 해줘도 모델 성능이 크게 향상 되지 않는 경우 ➡️ Model Iteration으로 선회
        - e.g., 여러 모델 아키텍쳐를 사용해보아도 모델 성능이 크게 향상 되지 않고, 최근 데이터를 사용하는 것이 모델 성능에 크게 기여하는 경우 ➡️ Data Iteration으로 선회
- *일반적으로, 모델 업데이트는 **‘가능한한 자주 업데이트’** 하는 것이 좋다*

### 9.2 프로덕션에서 테스트하기 
- 모델을 충분히 평가하려면 **오프라인 평가 + 온라인 평가를 혼합**해야 함
- 오프라인 평가만으로는 실제 프로덕션 환경에서의 성능을 보장할 수 없음
- 대표적인 오프라인 평가 방식: 테스트 분할, 백테스트

1. **테스트 분할 (test split)**
    - 가장 고전적인 오프라인 평가 방식
    - 정적 테스트 세트를 사용해야 함
    - 여러 모델을 비교하려면 동일한 테스트 세트를 써야 공정한 비교가 가능
    - 장점: 벤치마크 비교에 적합하며 재현성이 높음 !
    - 단점: 데이터 분포가 변한 상황을 반영하지 못하며, 과거 분포에서만 잘 작동하는 모델을 통과시킬 위험 있음

1. **백테스트 (backtest)**
- **과거 특정 시점의 데이터**로 예측 모델을 평가함. “과거 시점에서 이 모델이 실제로 잘 작동했을까?”를 시뮬레이션해보는 것
- 일반적으로 최근 데이터로 업데이트 → 직전 구간 데이터로 테스트
    
    ```sql
    1단계:
      학습: 1~3월
      테스트: 4월
    
    2단계:
      학습: 1~4월
      테스트: 5월
    
    3단계:
      학습: 1~5월
      테스트: 6월
    
    > 이런 식으로 시간을 따라서 데이터를 굴려보는 것
    ```
    
- 대표 방식
    - 확장 윈도(expanding window): 훈련 데이터를 시간에 따라 점점 늘림 (데이터 사이즈, 시간 범위 모두가 늘어남)
    - 슬라이딩 윈도(sliding window): 훈련 데이터 크기는 유지하고 시간축을 이동

  → 따라서 정적 테스트 세트로 **새너티 체크(sanity check)** 를 반복 수행해야 함

 **9.2.1 섀도 배포**

- 가장 안전한 프로덕션 테스트 방법으로, 새 모델을 실제 트래픽으로 테스트하되, 사용자에게는 절대 노출하지 않는 배포 방식
- 작동 방식
    1. 기존 모델과 후보 모델을 병렬 배포
    2. 요청을 두 모델 모두에 전달하되 사용자에게는 **기존 모델 결과만 제공**
    3. 후보 모델 결과는 기록 후 분석
    4. 새 모델 결과가 만족스러울 경우, 교체
- 장점: 사용자에게 예측 결과를 미리 제공하지 않기에 영향이 없어 위험을 최소화하는 편
- 단점: 추론 비용이 2배로 드는 등 전반적인 비용이 비싸짐

**9.2.2 A/B 테스트** 

- 기존 모델 vs 후보 모델 비교
- 트래픽을 무작위로 분할해 각 모델에 라우팅
- 작동 방식
    1. 두 모델 동시 배포
    2. 트래픽 일부를 새 모델에 할당
    3. 성능 차이를 통계적으로 검정
- A/B 테스트를 진행할 때의 중요 조건
    - 무작위성 필수: 선택 편향 발생 시 결과 무효
    - 충분한 샘플 수 확보: 통계적 유의성 확보 필요
- 통계적 유의성: 2-표본 검정 같은 통계적 가설 테스트 사용 + p-value 기반 판단
    
    → 다만, 통계적으로 유의하더라도 항상 옳은 선택이 아닐 수도, 둘 다 비슷하다는 결론이 나올 수도 있는 것. 또한 결과적으로 유의하지 않다면 두 모델이 거의 비슷할 가능성도 염두에 둬야 함 !
    

**9.2.3 카나리 배포**

- 소수 사용자부터 점진적으로 롤아웃
- 작동 방식
    1. 기존 모델과 함께 후보 모델 (= 카나리) 배포
    2. 일부 트래픽만 후보 모델에 라우팅
    3. 문제 없으면 점진적 확대
    4. 문제 발생 시 즉시 롤백하고 기존 모델로만 라우팅
- 장점: 위험 점진적 관리 + 실제 환경 검증 가능
- A/B 테스트와 유사하지만 반드시 무작위일 필요는 없음
    
    
    | 구분 | A/B 테스트 | 카나리 배포 |
    | --- | --- | --- |
    | 목적 | 어떤 모델이 더 좋은가? | 이 모델이 안전한가? |
    | 통계 검정 | 필수 | 선택 |
    | 무작위 분할 | 필수 | 선택 |
    | 편향 허용 | 안됨 | 어느 정도 가능 |

**9.2.4 인터리빙 실험**

- 두 추천 모델을 한 사용자에게 동시에 노출
- 클릭/사용자 선호도로 비교
- 사용자 그룹을 나누지 않고 추천 목록을 섞어서 제공하여 어떤 모델의 아이템이 더 많이 선택되는지 평가하는 방식

- 단점: 사용자 선호 ≠ 핵심 비즈니스 지표

**9.2.5 밴딧**

- A/B 테스트의 한계점 (무상태(stateless) + 중간 성능 고려 없이 트래픽 분배)에서 착안된 알고리즘으로, 보다 데이터 효율적임
- 탐색(exploration) vs 활용(exploitation) 균형
- 밴딧의 특징
    - 상태 유지(stateful)
    - 실시간 성능 기반 라우팅
    - 더 좋은 모델로 빠르게 트래픽 집중
- 필요 조건
    - 온라인 예측 가능
    - 빠른 피드백 루프
    - 성능 추적 메커니즘
- 주요 알고리즘: 데이터 효율성이 높고 기회비용의 감소가 가능하지만 구현이 복잡하고 빅테크에서만 주로 사용됨
    - ε-greedy
    - 톰슨 샘플링 (Thompson Sampling)
    - UCB (Upper Confidence Bound)
- 컨텍스트 밴딧: 모델이 아니라 ‘**행동의 보상**’을 최적화하는 메커니즘으로, 추천/광고에 적합함 !
    - 탐색-활용 트레이드오프의 대표 사례
    - 원-샷 강화학습 문제로 볼 수 있음
    
- 평가 파이프라인의 중요성: 좋은 평가 시스템은
    1. 어떤 테스트를 할 것인지
    2. 어떤 순서로 할 것인지
    3. 어떤 임곗값을 통과해야 하는지
    4. 누가 실행할 것인지
    
    를 명확히 정의해야 함 !
